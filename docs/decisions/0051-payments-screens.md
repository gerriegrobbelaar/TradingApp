# 0051 Payment screens: placement, wording, flows (Phase 9, P9c)

Status: accepted for P9c. NOTHING IN P9c MOVES MONEY and the screens work against the P9a API only. In production payments are OFF until P9b and its verification, so every screen is written to be honest about `payments_disabled`. Code: `apps/web/src/components/payments/`, `apps/web/src/pages/PaymentsSettings.tsx`, `apps/web/src/api-payments.ts`, `apps/web/src/lib/payment-labels.ts`, `apps/web/src/payments.css`. Rules from ADR 0043 (no optimistic UI, one label map, exact typed phrases, sheet stack, IBAN masking), ADR 0047 (lazy chunks, honest empty states) and ADR 0049 (the typed phrase, step-up) carry over.

## Where things live (the menu of CLAUDE.md 4.8 is not changed)

| Screen | Place | Why |
|---|---|---|
| Pay button, tick boxes, "Pay selected bills", Bank details | Purchases, Payables (extra columns) | the brief puts Pay on Payables |
| Payment approvals | Purchases, Approvals, tab **Payments** (`?tab=payments`); default tab **Bills in Exact** is the unchanged Exact screen | two kinds of approval, clearly named differently |
| Payments list and detail (status history, cancel) | Treasury, Bank, tab **Payments** (`?tab=payments`) | the menu is fixed; the Bank screen already has tabs for the lines a payment becomes |
| Settings, Payments | Settings, tab **Payments**, admin only | with the other admin settings |
| Supplier bank details | a sheet from Payables ("Bank details") | the relation id is on the bill row; the payment DTO does not carry it |

Not added to the menu: a new top-level entry would change CLAUDE.md 4.8. The Bank tab has no count (a count would need another request on every Bank visit and in every screens suite). It shows only when the bank has data (`available`), like the other Bank tabs; a request cannot exist before that.

## Words (one map: `lib/payment-labels.ts`)

- Every code in core (`PAYMENT_BLOCK_CODES`, `BATCH_BLOCK_CODES`, `PAYMENT_WARNING_CODES`, `APPROVAL_REASONS`, `PAYMENT_STATUSES`, `PAYMENTS_VERIFY_CHECKS`, the settings fields) and every refusal code in the worker's payment sources has a sentence; tests fail when a code is added without one (the worker sources are read with `import.meta.glob`). A block is two sentences: what is wrong, what to do. An unknown code gets one fixed generic sentence, never blank, never the server's text, never the code.
- Status words follow CLAUDE.md 4.3: `draft` Open; `pending_approval` Waiting for approval; `ready`, `submitting`, `submitted` Paying (with a sentence saying how far: "not sent yet" / "being sent" / "the bank has the instruction"); `paid` Paid; `failed` Failed (with the reason); `rejected`, `cancelled`, `expired` as named; `outcome_unknown` is **Not confirmed**, with the agreed sentence: "We could not confirm whether the bank received this payment. Do not pay again. An administrator can check it."
- "Paid" appears only when the server's status says `paid`. After a confirm the screen shows the status the answer reports (Waiting for approval, or Paying and "it has not been sent to the bank yet"), then re-reads. In drafts mode it adds that the payment waits as a draft in the Revolut app. `paid` is the bank's fact; booking the match in Exact is a separate step (ADR 0049, 0044) and the screen says so.
- Sentence case, no exclamation marks (scanned), lead with the number ("€ 1.234,56 to Acme"), amounts only through `formatMoney` on integer minor units.

## Flows

1. **Pay (one bill).** Pay opens the sheet. It reads the payment settings (`enabled`) and the bank accounts. Switched off: one sentence ("Payments are switched off, so nothing can be paid from this app yet."), a link to Settings, Payments for admins, the Review button disabled, no request made. Otherwise the person picks the source account (active, same currency, each with its last known balance and how old it is; none preselected) and presses **Review payment**. That creates a **draft** on the server (`POST /api/payments` with a random client key kept for the life of the sheet, so a repeat is the same request) which runs every pre-check. A 422 shows the blocks as sentences (and, for IBAN blocks, what the app knows about the bank account). A draft shows the confirmation: supplier, masked IBAN with "Verified by an approver" (a draft exists only for verified accounts; the badge says "First payment to these details" when a second person is needed for that reason), amount (and the EUR figure and rate), reference, source account and balance with its age, warnings, whether a second person is needed and why, expiry, then the phrase.
2. **Typed phrase.** `PAY <amount> <ccy> TO <last four>` is shown as text in a box; the field is empty and never pre-filled; pasting is allowed; the comparison is exact (core `phraseMatches`, case-sensitive, not trimmed). The phrase is **recomputed in the browser** from the amount and the masked IBAN on screen with core's `paymentConfirmPhrase`; if the server's `confirmPhrase` differs, the sheet refuses to continue ("does not match the amount shown here") rather than ask the person to type something they did not read. The server checks it again.
3. **Step-up.** `Me.stepUpFresh` false: the sign-in button is shown at once and Confirm is disabled; a 401 `step_up_required` from the server shows the same button. (The redirect loses typed text; the draft stays and is confirmed from Treasury, Bank, Payments.)
4. **Double submit.** One request at a time (`useAction`), the button disabled while it runs, and the server's client-key replay as the last line. A second click on Confirm sends one request (tested).
5. **Batch.** Tick boxes on payable bills (finance only), restricted to one currency and 50 bills (core `PAYMENT_BATCH_MAX_ITEMS`); the bar shows the count and total; the batch sheet lists the bills, asks for the account, then shows the per-bill list and `PAY BATCH n INVOICES <total> <ccy>`. A refused batch names the blocking bills.
6. **Approve.** Approvers see pending requests (Approvals, Payments), open one and see exactly what will be paid: summary, source account and balance, reasons, a 12-character **payload fingerprint** (the first 12 of the SHA-256; the full hash is sent back, never shown). Approve sends `{payloadHash}`; Turn down needs a reason of 3 or more characters. There are no buttons on one's own request ("You requested this payment, so someone else must approve it."), and the server's refusal (`self_approval`, `payload_changed`, `request_expired`, `approval_expired`, `not_pending`, `approver_lacks_role`, step-up) is explained in a sentence; after `payload_changed`, `not_pending` or any other refusal the sheet reads the request again so the person sees what it is now. Expired requests (`expired`, or past `expiresAt`) show no buttons. Nobody but an approver sees the buttons; finance and viewers read.
7. **Bank details (IBAN).** From Payables, "Bank details" for finance, approvers and admins. It shows the masked IBAN, the state in words, who confirmed it and when, and when the app last read it. An approver confirms by checking with the supplier by another route and typing the last four characters; the fingerprint sent back is the one the sheet read (a change in between is refused by the server). Approvers and admins can take a confirmation back. Finance is told to ask an approver.
8. **Payments list and detail.** Treasury, Bank, Payments: Open / Waiting for approval / Paid / Failed / All, "Only my requests", an "Updated x min ago" stamp, single payments and batches. The detail shows the same summary, the server's status and meaning, and the **history** from `payment_events`. **Cancel** (requester with the finance role, or admin; the server decides again): "Cancelling is final and cannot be undone", asked once; there is no undo toast anywhere in P9c because no payment action has an undo. `outcome_unknown` offers no cancel and says not to pay again.
9. **Settings, Payments.** The switch (read-only status; **Switch payments off** is offered because it is the safe direction and the server needs no phrase for it), what still blocks switching on (words per blocker), the verification checklist (Done / Not done per check), the Revolut plan, "Payment preview: Not available yet", "Sending to the bank: Not available yet" (the submitter), the approvers (count from the API and the list from `/api/users`), and the controls: mode, four-eyes toggle and limit, the new-IBAN rule, the two ceilings **marked Placeholder** (ADR 0049 question 3). Money is typed as decimal text and read with the allocation parser (BigInt; "0" allowed, more decimals refused, never rounded). Saving a tightening is direct. A loosening (core `loosenedFields`, the same function the server uses) opens the typed-phrase sheet (`LOOSEN PAYMENT CONTROLS`) and the server wants a fresh sign-in; the sheet explains what is loosened. A 409 `conflict` (the server compares the stored value in the write) explains itself and re-reads; a changed value while editing keeps the person's edits and offers "Use the saved values". Choosing one-click pay when the connection is not on the Company plan is refused on the screen before the server is asked. Verifying and switching ON are **not built** in this screen.

## Roles

`finance`: Pay, tick boxes, own drafts (confirm), cancel own; `approver`: approve, turn down, confirm and revoke bank details; `admin`: Settings, Payments, cancel any, revoke; `viewer`: reads the lists and details (no buttons); `approver` and `viewer` never see Pay. Roles are not hierarchical (as in the worker), so an admin does not see Pay. The server checks every role again.

## Privacy and money rules, tested

No full IBAN is ever held or shown (`****` mask and last four; a DOM test pushes full IBANs through every text field and scans HTML, values and the address; a source scan finds no IBAN literal). No float arithmetic (source scan: `Number(`, `Math.`, `toFixed`, division by 10/100/1000 and so on; the one conversion to a JSON number is `toSafeNumber`). Nothing is stored in the browser. Payment calls are made from `api-payments.ts` only (scan).

**Bug found and fixed while building:** the shared defensive IBAN mask (`maskDeep`) over-masks a SHA-256 in hex: 64 hex characters starting with two letters and two digits (about one hash in 20) look like an IBAN, so `payloadHash` came back as `AB12****34EF` and the approval was refused as a bad hash, intermittently. `api-payments.ts` masks every string EXCEPT the hex identifier fields (`payloadHash`, `ibanFingerprint`, `ibanFingerprintShort`, `requestId`, `providerId`, `protocolVersion`); tested with a hash that looks like an IBAN. Anything that parses text for IBANs on a field that can hold hex needs the same care.

## What changed outside the web (small, listed for the merge)

- `packages/core/src/api-types.ts`: the payment DTOs moved here **verbatim** from `apps/worker/src/payments/read.ts` in a delimited block, plus new response types for the web (`PaymentEventDto`, `PaymentListResponse`, `PaymentDetailResponse`, `SupplierIbanStatusDto`, `PaymentsSettingsResponse`, ...). `read.ts` re-exports `DecisionDto`, `PaymentDto`, `BatchDto` from core. A type test in core pins the three shapes against a literal copy of the P9a declarations (`Equal` check) and a worker test pins `IbanStatusDto` to core's `SupplierIbanStatusDto`.
- `apps/worker/src/payments/read.ts`: one read-only addition, `readEvents` (the append-only `payment_events` of one request, oldest first). `routes.ts`: `GET /api/payments/:id` and `GET /api/payment-batches/:id` now answer `{payment|batch, events}` (additive). Tested for every role, no IBAN.
- `apps/web/src/api.ts`: `ApiError` keeps the stable-code lists of a refusal (`blocks`, `blockers`, `loosened`, `warnings`, and a checked `itemBlocks`), nothing else of the body.
- `TypedPhraseSheet` takes an optional `describe` function (words for refusals).

## What is not built

- Verifying the payment path and switching payments ON from the screen (P9b adds the verification and preview endpoints; the checklist is shown read-only). The "Payment preview" row says "Not available yet".
- Pay only for **approved** bills is enforced by the server's pre-check (`invoice_not_approved`, `approval_unknown`, `approval_mapping_unverified`): the open-item list carries no approval status, so Pay is offered on every open, not "possibly paid" bill and the block is explained in the sheet. Showing the approval status in the row would need a join in the bills API.
- Part payments (the amount is always the full open balance; the API supports an amount, the settings default forbids it).
- Undo of any payment action (none exists), notifications to approvers (Phase 10 mail), the Today queue entry for payments, a relation id on the payment DTO (so an approver cannot open "Bank details" from a payment, only from Payables), the approver list from the settings answer (the screen reads `/api/users`, admin only).
- An EUR-equivalent total for a mixed-currency view, and a count on the Bank tab (above).

## Open questions

1. Should Pay be hidden until the bill is known to be approved (needs the approval status on `OpenItemRow`), instead of explained after the click?
2. Should an approver be able to open a payment's supplier bank details from the approval (needs `relationId` on `PaymentDto`)?
3. Should "Switch payments off" stay on this screen while switching ON is not built? It is the safe direction and audited.
4. Is "Not confirmed" the right chip for `outcome_unknown`, or should it say "Check with the bank"?

## Review P9c (changes made by the reviewer)

- **Client key per payload, not per sheet.** The key is kept per (source account, bills) for the life of the sheet: a retry after a lost answer sends the same key (the server replays the draft it already made), choosing another account sends another key (a key is never reused for a different payload, which the server would refuse as `client_key_reused`), and going back to the first account sends the first key again. A new opening of the sheet is a new decision and a new key; the server's `already_in_request` stops a second open request for the same bill.
- **The draft must be the one asked for.** The sheet checks the server's draft against what it asked for (same bills, same account, same currency). If not, it refuses to show the phrase ("cannot be confirmed here") and says to look at it in Treasury, Bank, Payments. If Exact's open amount moved, the sheet says so with the list's amount; the phrase follows the server's amount.
- **A changed payload drops the typed phrase** (the confirm panel is keyed by the payload hash).
- **A payload that changes under an approver** (a re-read after a refusal, "Check status again", the quiet refresh on focus) disables Approve and Turn down and shows both fingerprints until the approver presses "I have read the new details". The hash sent is then the new one, exactly.
- **Masking keeps identifiers exact everywhere.** `lib/mask.ts` `maskDeep` (used by the payments, matching and data quality APIs) keeps a field unmasked only when its key is a known identifier AND the value has that identifier's exact shape (64 hex for hashes and fingerprints, 16 hex for the short fingerprint, a UUID for request and provider ids, base64url/digits for cursors). The matching queue cursor is base64url and could be corrupted by the old mask after a `-` or `_`; a full IBAN put in an identifier field by mistake is still masked. Request bodies are built from ids, the typed text and the hash, never from masked display text (tested: the hash and the fingerprint sent are IBAN-looking and arrive unchanged).
- **Unknown failures do not promise "nothing was paid".** An unknown refusal or no answer at all says to check the status in Treasury, Bank, Payments before trying again (the same sheet would send the same key).
- **Settings, Payments sends only this person's edits.** The form remembers the settings it was built from; the PATCH carries only the fields edited since, applied on top of what is stored now, so a ceiling somebody else changed meanwhile is not set back silently (the server applies a PATCH on top of its current settings). The "Somebody else changed these settings" notice now really shows (it never did: the base moved with every read). When the server says a change loosens a control the screen did not see as one (400 `confirmation_required` with `loosened`), the typed-phrase sheet opens with the server's list.
- Batch view: a Reference column per bill. Pay sheet: a sign-in button before the draft when the sign-in is old, so the redirect does not leave a half-done sheet. Bank details: after a refused confirmation or revoke the sheet shows what the server holds now.
- Worker: `GET /api/payment-batches/:id` history tested for every role, without an IBAN, one row per batch move.

### Answers to the open questions (recommendations)

1. **Pay only when approved:** yes, eventually: show the Exact approval status on `OpenItemRow` (a join in the bills read) and offer Pay only on approved bills; keep the server pre-check as the guard. Not small (API change), so not done here; the block sentence after the click is honest meanwhile.
2. **`relationId` on `PaymentDto`:** yes, additive and useful (an approver opens the bank details from the approval). It changes the pinned P9a shape, so it belongs in a worker task with its own pin update, not in this review.
3. **Switch payments off on this screen:** keep it. It is the safe direction, admin only, asked once and audited (`payments.disabled`).
4. **Chip for `outcome_unknown`:** keep "Not confirmed" (short, true, not alarming in a list) with the fixed sentence "Do not pay again. An administrator can check it." next to it in every detail view.
