# ADR 0021: Scheduler, job queue and the JobLock lease
Status: accepted (task H2, Phase 3)

## Context
CLAUDE.md 4.1: jobs with a schedule in Europe/Amsterdam, `job_runs` history, no self-overlap, safe to retry, "Run now" from Settings. Cloudflare gives us Cron Triggers (UTC only, a handful per Worker), Queues and Durable Objects.

## Decision
- **One cron, every minute** (`* * * * *`). The Worker decides which jobs are due from `jobs.schedule_json` (`packages/core` `isDue` / `nextRun`, Amsterdam wall clock, daylight saving aware). This is why a schedule can be edited in the app with no deploy, and why the 5-cron limit does not matter. The stopgap hourly cron is gone.
- **Claim, then queue.** For a due job the tick inserts a `job_runs` row `queued` with `UNIQUE (job_id, scheduled_for, attempt)` (`scheduled_for` is the schedule slot, computed the same way by every isolate), moves `jobs.last_scheduled_at` / `next_run_at` in the same batch, then sends `{runId, jobId}` to the `camelthorn-jobs` queue. Duplicate ticks and overlapping isolates lose the insert and do nothing. Missed slots (an outage) collapse into one run because the baseline moves to "now", not to the slot. A new job, a changed schedule or a job switched on starts counting from that moment: nothing fires for the past.
- **Consumer.** `queue()` runs one message per invocation (`max_batch_size = 1`, own subrequest budget). `executeRun` is idempotent per run: finished runs are acked and ignored; a run `running` with a fresh heartbeat is retried later; a run whose heartbeat is older than 2 minutes is taken over. Only the holder of `runner_token` may finish a run, so a taken-over executor cannot overwrite the new result.
- **No overlap: `JobLock` Durable Object per job name** (`job:<name>`, EU jurisdiction via `getEuObject`). `acquire(holder, ttl)` grants a 90 s lease; the executor heartbeats every 30 s (and aborts the handler's signal if the lease is lost), releases in `finally`, and a dead isolate's lease just expires. A run that cannot get it is recorded `skipped` with code `already_running`. Manual "Run now" goes through the same queue, consumer and lock. A D1 lease (as in `sync_locks`) was considered; a Durable Object is single-threaded, needs no clock comparison in SQL and is what CLAUDE.md prescribes for locking.
- **Sweep.** Every tick re-sends messages for runs untouched for 5 minutes (a crash between insert and send, a lost delivery) up to 4 sends, then marks them `error` with code `abandoned`. Finished runs are deleted after 90 days.
- **Handlers** are registered by key in `jobs/handlers.ts`. A job whose phase is not built has a handler without `run`: runs are recorded `skipped` / `not_implemented`, "Run now" is refused (409), and the job ships disabled. Handlers get `{env, job, run, trigger, budget, deadlineMs, signal, log}`, return `{status, summary, code?, retry?}`, run under try/catch and a timeout, and store counts and codes only (masked by `maskDeep`, capped at 4,000 characters).
- **Retries.** A handler may ask for a re-run (`retry.delaySeconds`); the runner inserts attempt n+1 of the same slot (trigger `retry`) and sends it with a queue delay, up to the handler's `maxAttempts`. Manual runs and errors are never retried. A thrown error that `sync.ts` classifies as transient becomes `partial` and retries; anything else is `error`.
- **Exact jobs.** `exact.full_sync` (02:00 daily, 240 calls per administration and attempt, 4 attempts, 5 minutes apart; a retry skips administrations that finished today) and `exact.incremental_sync` (hourly at :30 so it does not meet the nightly run, which shares the per-division sync lease; 40 calls). Worst case per administration and day: 4 x 240 + 25 x 40 = 1,960 of Exact's 5,000.
- **Seeding.** Default jobs are written at Worker start (`jobs/defaults.ts`), guarded by a `seed.default_jobs` version marker in `settings`; applying a version inserts missing jobs by name and never touches existing rows, so admin edits survive restarts and releases. A new default job = add it and bump `DEFAULT_JOBS_VERSION`.
- **API** `GET /api/jobs`, `GET /api/jobs/:id/runs`, `PATCH /api/jobs/:id` (admin, no step-up, audited with the change in one batch, guarded by a `rev` token, budget 1..1000 and only for Exact jobs), `POST /api/jobs/:id/run` (admin or finance; 409 while queued or running, 429 within 30 s of the last manual run, audited). The screen is told whether the queue binding exists and when the tick last ran, and warns if not.

## Review additions (H2 review)
- **Takeover vs a live executor.** A redelivery that finds a run `running` with a stale D1 heartbeat takes the row, then asks the lock. If the lease is still held by that run's own previous executor (`AcquireResult.holder === runner_token`), the executor is alive and only its D1 writes failed: the row is put back exactly as it was and the delivery retries later. Before, the run was recorded `skipped` / `already_running` while it was in fact working, and its real result was then thrown away.
- **Overlap is bounded by the lease, and abort is cooperative.** Two executors of one job can only overlap if the lease expired, i.e. the DO heartbeat failed for 90 s (three beats). The old executor learns it at its next beat and its signal is aborted; after a 30 s grace the runner stops waiting, but JavaScript cannot kill the handler's promise, so handlers must check `ctx.signal` between steps (the Exact jobs check it before every administration, and the per-division `sync_locks` lease still prevents two syncs of one administration). The old executor can never record a result (`runner_token`).
- **Delayed retries and the sweep.** A retry row's `enqueued_at` is the moment its delayed message becomes visible (now + delay), so the sweep (5 minutes) does not send a duplicate of a 5 to 10 minute delayed retry. Delays are clamped to 0..12 h (Queues maximum).
- **Tick cost.** Per tick with nothing due: one conditional upsert of the tick stamp that writes a row at most every 4 minutes (`TICK_STAMP_EVERY_MS`), one SELECT of enabled jobs (8 rows), one indexed sweep SELECT, no batch. The screen warns when the stamp is older than 10 minutes. The seeds run once per isolate (memoised).
- **Concurrency token from the client.** `GET /api/jobs` returns each job's `rev`; the screen sends it with `PATCH`; a stale one is 409 `conflict` with nothing written. Without `rev` (API clients) the read-then-write guard still applies.
- **Schedule errors.** 400 `schedule_invalid` with `message`, the sentence from `validateSchedule` (ADR 0020); the editor shows the same sentence live.
- **Migration 0008** keeps old run ids, closes runs the old code left `running` as `error` / `abandoned` (so the sweep never re-sends them) and numbers old runs with the same start time as attempts 1, 2, ...
- **Limits (Workers paid plan, checked November 2026).** A queue consumer invocation may run 15 minutes wall time; CPU time is 30 s by default (`[limits] cpu_ms` raises it to 5 minutes). Runs stop at 13 minutes plus 30 s grace (`RUN_TIMEOUT_MS`), the Exact jobs at 12 minutes (`SYNC_MAX_MS`). The sync is I/O bound; if a run ever ends with an exceeded-CPU error, set `cpu_ms` rather than raising budgets. Lease 90 s / heartbeat 30 s / stale 2 min / sweep 5 min are independent of these limits.
- **DST.** Per ADR 0020 the hourly incremental sync fires 25 times on the fall-back day; the 1,960 calls/day bound is now derived in a test by counting real `nextRun` fires per Amsterdam day over 2026-2027.

## Consequences
- Setup needs two queues created by hand (`docs/DEPLOY.md`); the deploy check refuses a config without the cron, the `JobLock` class and migration `v2`, the producer, the consumer and the dead-letter queue.
- Disabling a job does not cancel a run already queued; the consumer records it `skipped` / `disabled` (manual runs still run).
- "Run now" can add calls on top of the scheduled worst case; the gate's own 5,000 per day limit still applies.
- Tests call `executeRun` and `handleQueue` directly with a recording fake queue instead of the Miniflare queue, so delivery timing is under test control. Test seam: `RunnerDeps`.

## Verify on first deploy
Queue and dead-letter queue exist; Settings, Schedules shows no warning within 2 minutes; "Run now" on the incremental sync ends `OK`; `JobLock` objects appear under the EU jurisdiction.
