# 0054 Payments in the web: Send to bank, honest "Paid", admin tools (F9c)

Status: accepted for F9c (Phase 9 final-review blockers B1 and B2). Builds on ADR 0049 (foundation), 0050 (execution) and 0051 (screens). Payments are still OFF by default (twelve gates, see the Phase 9 review); this change makes the web able to drive the whole path once an administrator has switched it on, and stops the web from calling a payment "Paid" before it is.

## B2: "Paid" means the bank confirmed AND the match is booked in Exact (CLAUDE.md 4.3)

- `PaymentDto.settlement` (core `api-types.ts`, codes `PAYMENT_SETTLEMENTS`: `not_paid`, `awaiting_bank_line`, `awaiting_match`, `match_other_invoice`, `awaiting_booking`, `booked`) is filled by `apps/worker/src/payments/read.ts` from the EXISTING `paymentSettlement`. Only a `paid` row is looked up; every other status is `not_paid` without a query. A failed lookup reads as `awaiting_bank_line`, never as `booked`. Additive: the P9a fields are byte-identical (type test: the old copy of the DTO plus exactly this field). The items of a batch carry their own settlement.
- A batch has no settlement of its own in the API. The web takes the least advanced item (`batchSettlement`): all items `booked` = booked; any item further back, no items, or one code this version cannot read = not booked.
- ONE place decides the words: `lib/payment-labels.ts` `displayStatus(subjectOf(dto))`.
  - `paid` + `booked` = **Paid** (green).
  - `paid` + anything else, an unknown code, or no settlement = **Paid at the bank, booking pending**, with the step in words: waiting for the bank line, waiting for the match, "matched elsewhere" (`match_other_invoice`: label "Paid at the bank, matched elsewhere", warning tone, check the match before paying anything else), match made but not booked ("it stays here while booking in Exact is switched off"). One map, `SETTLEMENT_TEXT`; unknown code, `SETTLEMENT_FALLBACK` (never "Paid").
  - `submitted` in drafts mode = **Waiting for approval in Revolut** ("Open the Revolut app and approve it there. Nothing is paid until you do."); in pay mode it stays "Paying". `outcome_unknown` is unchanged ("Not confirmed", "Do not pay again").
  - `STATUS_TEXT.paid` itself is no longer "Paid".
- A request the bank paid is not final until booked: the detail sheet keeps re-reading it and keeps "Check status again".
- List filter: "Paid" became "Paid at the bank" (the server filter is by status; each row says whether it is also booked). The Pay sheet, detail sheet, tables and toasts all use `StatusChip`/`StatusPanel`.
- A source scan (`payments-paid-scan.test.ts`) fails when any screen file outside `lib/payment-labels.ts` compares a status with the paid value, names the paid literal, uses `STATUS_TEXT`/`statusText` for display, or hard-codes a "Paid" label. The one allowed use of `PAID_STATUS` is the list filter's wire value.
- Other screens: Payables has no paid marker (a bill is "Check first" until Exact shows it paid); Today has no payment item yet (F9b); there is no export of payments. The Bank screen's "Paid"/"Received" words are about completed BANK TRANSACTIONS by direction, not payment requests, and are unchanged.

## B1: Send to bank

- Where: `components/payments/SendPanel.tsx`, shown in the request view (Pay sheet, Treasury detail, approvals) when the status is `ready` AND the user has the `finance` role. Approvers, viewers and administrators without finance see nothing (the route needs finance + a fresh sign-in; the server enforces it again). Any finance user may send, not only the requester (the route's rule; the four-eyes approval is what binds the payload).
- Flow: the button opens a confirmation INSIDE the sheet (an inline section, focus moves to its heading; "Back" returns focus to the button), not a second sheet on top of a sheet. It restates supplier, masked IBAN, amount, reference, source account and mode (batch: total and each bill), and what happens next: drafts, "A draft is created in Revolut. You must approve it in the Revolut app. Nothing is paid until you do."; pay, "The bank pays immediately." The button of the confirmation (`Create the draft in Revolut` / `Pay now`) is the only thing that calls `POST /api/payments/:id/submit` or `/api/payment-batches/:id/submit`. A stale sign-in disables it and shows the sign-in button.
- Idempotency: the submit routes take no client key. The idempotency is the server's claim (`payment_claims`, the send ledger, `already_claimed`). The web adds a single-use guard: one call per decision, a double click is one request, a refusal re-arms it, anything else does not.
- Result handling (`lib/payment-send-labels.ts`, one map from the worker's stable codes):
  - 200 with `result.to`: `submitted` (drafts: "The draft was created in Revolut. Open the Revolut app and approve it there..."; pay: "The bank has the instruction. It shows as paid only after the bank confirms it and the payment is booked in Exact."), `rejected` ("The bank did not take this request. Nothing was paid." plus the reason from `provider_rejected:<code>`), `outcome_unknown` ("We could not confirm whether the bank received this. Do not send it again. An administrator can check."). Success is shown ONLY for `submitted`; a 200 whose `result.to` this version cannot read is "unsure", not success.
  - 409/404 with a code = a REFUSAL made before anything was claimed: its own sentence ("... so nothing was sent"), the confirmation closes, the Send button stays for a later try. Codes: every `refused` code of `submit.ts`, `whyNot`, the gate lease (`busy`, `owner`, `connection`, `connection_mismatch`, `payments_<gate reason>`), `payment_lease`, the approval denials (`approval_<denial>`), the pre-check codes (`precheck:<block>` is worded through the block map), `controls_changed`, `payload_changed`, `iban_binding_broken`, `pay_mode_not_verified`, `submitter_unavailable`, `requester_inactive` (added by F9a), `already_claimed`; the bank-side refusals `prior_attempt_live`, `prior_attempt_unchecked`, `counterparty_account_ambiguous` and the `counterparty_*` family. A test READS these codes from the worker source and fails when one has no sentence. An unknown code gets one fixed sentence, never the server's text.
  - Anything else (a 5xx, a timeout, no connection, an unreadable 200) is NOT a refusal and never promises "nothing was sent": "We could not confirm what happened. Do not send it again. An administrator can check." The Send button is gone for the rest of that opening of the sheet, and the request is re-read. After an `outcome_unknown` the status itself removes the button.
- `ready` is now "Approved, not sent yet" everywhere (labels, the confirm panel's "queued" text, the status panel). The drafts-mode note is shown only once something was sent.
- Status reasons (B1 wording): `draft_expired` "The draft was not approved in time. If it is still in the Revolut app, delete it there before asking for a new payment." (shown as a warning, not a footnote), `bank_declined`, `bank_reverted`, `bank_failed`, `resolved_not_sent`, `provider_rejected:<code>`; unknown reason = "No further reason was recorded." Timeline words for `reconciled_pending`, `bank_*`, `draft_expired`, `resolved_not_sent`. A failed request now says "The payment was not made." (it no longer blames the bank when the cause is an expired draft).

## Admin tools in Settings, Payments (admin only; every write needs a fresh sign-in where the server asks for it)

- **Switch on** (typed phrase `ENABLE PAYMENTS`, optional note). The button is off while the settings answer lists a blocker (other than "the switch is off"), and the blockers are printed above it (including `pay_mode_not_verified`). A 409 `blocked` from the server is worded from its `blockers` list.
- **Record the verification**: one tick box per code in `verifyChecks` (rendered from the API list, so a check added later appears without a release; text from `verifyRunbook[code]` when present, else the label map, else a generic line), each with its runbook steps and pass condition in a `details`. The complete list, a note of at least 10 characters and the phrase `I VERIFIED THE PAYMENT PATH ON THE REVOLUT SANDBOX` are needed. The ticks live in React state only: nothing in localStorage/sessionStorage/cookies, closing the sheet loses them (it asks first when something is ticked). Recording a verification leaves payments OFF; the sheet says so.
- **Draft expiry days** (1 to 30, whole number, parsed as text, never as a float).
- **Unknown outcomes**: lists `outcome_unknown` payments and batches with their age, explains the rule (Revolut must have been asked at least 15 minutes after the request became unknown, in the last 30 minutes, and said it has no such payment; the server decides), and `MARK PAYMENT AS NOT SENT` with a warning that a wrong answer can mean a second payment.
- **Preview payment**: kind + request number; shows each call (step, path, "accepted by the gate", payee placeholder), the SHA-256 (rendered when present; a step without a hash says so, because F9a may stop hashing the counterparty body, review S7) and the body as the server sends it, which is IBAN-masked on the server and masked again in the browser (`sha256` is an identifier field in `lib/mask.ts`). No full IBAN is ever rendered (DOM test with a deliberately leaking mock).

### Not built, and why

- No partial "verify progress" save: the base has no such endpoint and a half-saved checklist stored in the browser would break "nothing stored client-side". The sheet sends the complete list at once. If F9a adds a progress endpoint, wiring the ticks to it is a follow-up.
- No staging-only provisional verification mark and no fault switch for the lost-answer drill (review S3 belongs to F9a/DEPLOY, not the web).
- No acknowledge button for payment alerts (F9a's endpoint, DQ and Today are F9b's).
- Revoking a supplier IBAN, and `PATCH` of the controls, were already in the UI (P9c).

## Accessibility and quality

Real buttons, radios and checkboxes; the preview body is a focusable, labelled `pre`; the confirmation moves focus and gives it back; colours come only from tokens already in `payments-contrast.test.ts` (new text pairs added there); no transitions (reduced motion); sentence case, no exclamation marks, numbers from `lib/format`; `payments-scan` (no float arithmetic, no browser storage) covers the new files. Everything is in the existing lazy chunks (`PaymentParts`, `PaymentsSettings`; `SendPanel` rides with `PaymentParts`, `PaymentAdminTools` with `PaymentsSettings`).
