# 0016 Exact OAuth and API assumptions (verify with real credentials)
Status: open, 2026-11-10 (updated with review G2: items 16-19 and the live checklist)

No Exact credentials existed when this was built; everything was tested against a stubbed `fetch`. CLAUDE.md 3 says to re-check the API docs. Each item below is from memory of Exact's documentation and must be confirmed on the first real connection. Where the item is wrong, the fix is local (a constant or one parser) as noted.

1. **Endpoints.** Authorize: `https://start.exactonline.nl/api/oauth2/auth` with `client_id`, `redirect_uri`, `response_type=code`, `force_login=0`, `state`. Token: `POST https://start.exactonline.nl/api/oauth2/token`, form-encoded, `client_id` and `client_secret` in the body (not HTTP Basic). Code in `exact/oauth.ts`.
2. **No PKCE.** Exact is assumed not to support PKCE or a `nonce`; CSRF protection is `state` in a signed single-use cookie bound to the admin's email. If Exact now supports PKCE, add it (the flow cookie already has a `verifier` field).
3. **Token response.** `{access_token, token_type, expires_in, refresh_token}` with `expires_in` as a string of seconds (about `"600"`). Parsed with `Number()`.
4. **Refresh token rotation.** Each refresh returns a new refresh token and the old one stops working; refresh tokens last about 30 days from issue. If tokens do not rotate, the persist-first order is merely redundant.
5. **Error body.** A revoked or reused refresh token answers HTTP 400 with `{"error":"invalid_grant"}`. Anything else 4xx is treated as our configuration problem (tokens kept); 5xx and 429 as transient.
6. **Authorization codes** are single use and expire within a few minutes.
7. **`/api/v1/current/Me`** returns `{"d":{"results":[{"CurrentDivision":123456, "DivisionCustomerName":"...", ...}]}}`. `parseMe` also accepts `d` as an array and falls back to `Division <n>` if the name field is absent. The full list of divisions a user can reach (for example `system/Divisions`) is not read yet; only the current division is stored. Division currency defaults to EUR until the sync reads it.
8. **Rate-limit headers.** `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (daily, reset as epoch milliseconds) and `X-RateLimit-Minutely-Limit`, `-Remaining`, `-Reset`. Seconds-valued resets are tolerated (values below 1e11 are multiplied by 1000). `Retry-After` on 429 may be absent; then the reset headers, then 60 s are used. The daily window is assumed to reset at midnight UTC when Exact gives no reset time (it may be midnight in another zone; the header wins when present). Code in `exact/gate.ts` `readRateHeaders` / `blockFor429`.
9. **Limits.** 60 calls/minute and 5,000/day per division are CLAUDE.md figures; the actual limits can differ per app and are overridden by the headers when sent.
10. **XML API.** `https://start.exactonline.nl/docs/XMLUpload.aspx?Topic=...&_Division_=<n>` accepts `Authorization: Bearer` (OAuth) and takes the division as the `_Division_` query parameter. The XML paths allowed are only `/docs/XMLUpload.aspx` and `/docs/XMLDownload.aspx`. E3/E-matching must confirm the parameter name and that bearer auth works for MatchSets.
11. **Regional host.** Fixed to `start.exactonline.nl` (CLAUDE.md). `connections.region_host` exists and is validated against an allow-list of Exact hosts, but the OAuth start route does not read it yet.
12. **Revocation.** Exact has no known revoke endpoint, so Disconnect only deletes our copy of the tokens. An admin should also remove the app grant in Exact (My Exact Online, Connections) when decommissioning.
13. **Redirect URI** registered on the Exact app must match `EXACT_REDIRECT_URI` exactly; local development needs a second registration for `http://localhost:5173/...` if Exact allows http.
14. **Single connection.** One `exact` connection per deployment. A user with access to several Exact accounts would need one connection per account.
15. **`jobs.exact_budget`.** The task text said `jobs.budget`; the schema column is `exact_budget` (migration 0003). The gate reads that.
16. **Minimum token age (UNVERIFIED, from the phase 2 reviewer's recollection).** Exact is believed to reject a refresh until the access token is at least about 570 s old (tokens live 600 s). Implemented defensively in `exact/gate.ts`: `MIN_REFRESH_AGE_MS = 570_000`, `REFRESH_MARGIN_MS = 600 - 570 = 30 s`. A call that needs a token with 30 s or less left (age 570 s or more) triggers the refresh, so a refresh happens at age 570-580 s when calls keep arriving (a call needs about 20 s of life left to finish, hence 580 s as the intended latest point); with no traffic the token simply expires and the next call refreshes (late is legal). Token age comes from a record in the authority's storage (`issued:<id>`, written on every refresh) or, failing that, `expires_at - 600 s`. If a token is inside the margin but younger than 570 s (the real lifetime is shorter than assumed) the refresh waits up to 30 s; if it would wait longer, the still-valid token is used. A 401 forces a refresh only when the token is older than 570 s; otherwise the call waits 2 s and retries once, and a second 401 is a retryable 503 `token_refresh_retry`, never an auth error. If the real minimum is not 570 s, change the two constants.
17. **Premature-refresh rejection (body UNKNOWN).** We do not know what Exact answers to a too-early refresh (status and body). Every 4xx other than a clear `{"error":"invalid_grant"}`, every redirect and every body we cannot classify is treated as retryable: tokens and status are kept, the authority retries twice after 5 s and 15 s, then falls back to the still-valid access token (cooldown 10 s before the next attempt) or answers a retryable 503 `token_refresh_retry`. Only `invalid_grant` (or a success body we cannot parse, after which the old refresh token may be spent) wipes the tokens and sets `needs_reauth`. Consequence: a genuinely wrong client secret (`invalid_client`) also shows as retryable, not as re-authorise; the log/last_error will show `token_refresh_retry` repeatedly. If Exact's too-early answer is in fact `invalid_grant`, this rule would wrongly wipe tokens: check on the live connection (checklist item 3).
18. **Minute limit window (UNKNOWN).** Whether Exact's per-minute limit is a rolling window or a fixed clock minute is unknown. The gate enforces the stricter reading: a sliding-window log, never more than 60 calls in any 60 s (review S1). `X-RateLimit-Minutely-Remaining` can only tighten it for the reported reset time.
19. **Rotated tokens and a failing D1.** After a refresh the new pair is written to D1 (two attempts). If both fail, the encrypted pair is kept in the authority's Durable Object storage (`pending:<id>`, ciphertext only, same AAD), used from there, and written to D1 by the next call or an alarm every 30 s until it succeeds; it is dropped when the connection is no longer active. This replaces the earlier rule that a failed write set `needs_reauth` (the old refresh token is dead after rotation, so that forced a needless re-authorisation). If DO storage also fails, `needs_reauth` still applies.

## Live connection checklist (add to ADR 0017 / DEPLOY.md verification)
1. Refresh at age 540 s (should be rejected or refused by us), at 570 s and at 580 s; record Exact's answer (status, body) to the early attempt. Confirm `expires_in` is 600.
2. Confirm that a 401 on a young token does not happen in normal use; if it does, find out why.
3. Provoke `invalid_grant` (revoke the app grant in My Exact Online) and confirm the body is `{"error":"invalid_grant"}` and that `needs_reauth` is then set once, with one audit row.
4. Confirm the refresh token rotates and that its lifetime is about 30 days.
5. Under load for one full minute, check whether the minute limit is rolling or clock-aligned, and what `X-RateLimit-Minutely-*` report.
6. Confirm DO objects show jurisdiction EU (ADR 0018).
