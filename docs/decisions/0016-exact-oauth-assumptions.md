# 0016 Exact OAuth and API assumptions (verify with real credentials)
Status: provisional — verify with credentials (updated in review G2: items 16-20 and the live checklist; in G3: items 7, 8, 11 and checklist 8-10)

No Exact credentials existed when this was built; everything was tested against a stubbed `fetch`. CLAUDE.md 3 says to re-check the API docs. Each item below is from memory of Exact's documentation and must be confirmed on the first real connection. Where the item is wrong, the fix is local (a constant or one parser) as noted.

1. **Endpoints.** Authorize: `https://start.exactonline.nl/api/oauth2/auth` with `client_id`, `redirect_uri`, `response_type=code`, `force_login=0`, `state`. Token: `POST https://start.exactonline.nl/api/oauth2/token`, form-encoded, `client_id` and `client_secret` in the body (not HTTP Basic). Code in `exact/oauth.ts`.
2. **No PKCE.** Exact is assumed not to support PKCE or a `nonce`; CSRF protection is `state` in a signed single-use cookie bound to the admin's email. If Exact now supports PKCE, add it (the flow cookie already has a `verifier` field).
3. **Token response.** `{access_token, token_type, expires_in, refresh_token}` with `expires_in` as a string of seconds (about `"600"`). Parsed with `Number()`.
4. **Refresh token rotation.** Each refresh returns a new refresh token and the old one stops working; refresh tokens last about 30 days from issue. If tokens do not rotate, the persist-first order is merely redundant.
5. **Error body.** A revoked or reused refresh token answers HTTP 400 with `{"error":"invalid_grant"}`. Anything else 4xx is treated as our configuration problem (tokens kept); 5xx and 429 as transient.
6. **Authorization codes** are single use and expire within a few minutes.
7. **`/api/v1/current/Me`** returns `{"d":{"results":[{"UserID":"...","CurrentDivision":123456,"DivisionCustomer":"<guid>","DivisionCustomerName":"...", ...}]}}`. The connect callback reads it with the shared client function `fetchCurrentMe` over the gate's division-0 transport (the hand-written `parseMe` is gone). The current division is stored enabled for syncing (name from `DivisionCustomerName`, else `Division <n>`); the full list (`system/Divisions`, with its `Currency`) is read by every sync and its other divisions are stored disabled (ADR 0019). `DivisionCustomer` / `DivisionCustomerName` give the account identity that detects a reconnect to a different Exact account. The field names are from memory: verify.
8. **Rate-limit headers.** `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (daily, reset as epoch milliseconds) and `X-RateLimit-Minutely-Limit`, `-Remaining`, `-Reset`. Seconds-valued resets are tolerated (values below 1e11 are multiplied by 1000). `Retry-After` on 429 may be absent; then the reset headers, then 60 s are used. The daily window is assumed to reset at midnight UTC when Exact gives no reset time (it may be midnight in another zone; the header wins when present). The headers are parsed by the one shared `parseRateLimitHeaders` / `retryAfterFromHeaders` (`packages/exact/src/rate-limit.ts`); the gate's `readRateHeaders` / `blockFor429` in `exact/gate.ts` decide what they change (only ever tighter).
9. **Limits.** 60 calls/minute and 5,000/day per division are CLAUDE.md figures; the actual limits can differ per app and are overridden by the headers when sent.
10. **XML API.** `https://start.exactonline.nl/docs/XMLUpload.aspx?Topic=...&_Division_=<n>` accepts `Authorization: Bearer` (OAuth) and takes the division as the `_Division_` query parameter. The XML paths allowed are only `/docs/XMLUpload.aspx` and `/docs/XMLDownload.aspx`. E3/E-matching must confirm the parameter name and that bearer auth works for MatchSets.
11. **Regional host.** One constant, `DEFAULT_EXACT_HOST` (`start.exactonline.nl`, in `@camelthorn/exact`, re-exported by `exact/config.ts`), is used by the authorize redirect, the code exchange and the value stored in `connections.region_host` at connect time. Later API calls and refreshes use the STORED `region_host`, validated against an allow-list of Exact hosts (`isExactHost`) before any request or token POST, so a poisoned value cannot send a bearer token elsewhere. The OAuth start route never reads the stored value, so a Belgian or German instance needs a code change (and a second app registration) before it works.
12. **Revocation.** Exact has no known revoke endpoint, so Disconnect only deletes our copy of the tokens. An admin should also remove the app grant in Exact (My Exact Online, Connections) when decommissioning.
13. **Redirect URI** registered on the Exact app must match `EXACT_REDIRECT_URI` exactly; local development needs a second registration for `http://localhost:5173/...` if Exact allows http.
14. **Single connection.** One `exact` connection per deployment. A user with access to several Exact accounts would need one connection per account.
15. **`jobs.exact_budget`.** The task text said `jobs.budget`; the schema column is `exact_budget` (migration 0003). The gate reads that.
16. **Minimum token age (UNVERIFIED, from the phase 2 reviewer's recollection).** Exact is believed to reject a refresh until the access token is at least about 570 s old (tokens live 600 s). Implemented defensively in `exact/gate.ts`: `MIN_REFRESH_AGE_MS = 570_000`, `REFRESH_MARGIN_MS = 600 - 570 = 30 s`. The earliest refresh is `min(issued + 570 s, expires - 30 s)`: with `expires_in` 600 both are the same moment; with a shorter lifetime the minimum age scales down (a fixed 570 s on a 300 s token would leave no valid token for 270 s), and an expired token can always be refreshed. A division gate asks the authority for a new token once 30 s or less are left (exactly 30 s left = age 570 s refreshes; 30.001 s left does not), so with steady traffic the refresh happens at age 570-580 s; with no traffic the token simply expires and the next call refreshes (late is legal). Token age is measured on the authority's clock from when the token response arrived, which is later than Exact issued it, so clock skew can only make us refresh later, never earlier. The issue time comes from a record in the authority's storage (`issued:<id>`, written after every refresh, best effort) or, failing that, `expires_at - 600 s`; a token with more than 600 s left and no record counts as old enough. If a refresh is somehow needed before the earliest point the authority waits up to 30 s, else uses the still-valid token. A 401 forces a refresh only when the token is past the earliest point; otherwise the call waits 2 s and retries once, and a second 401 is a retryable 503 `token_refresh_retry`, never an auth error. The same applies when the authority hands back the token Exact just rejected (it joined a refresh that reused it, or credentials are being rejected). If the real minimum is not 570 s, change the two constants.
17. **Premature-refresh rejection (body UNKNOWN).** We do not know what Exact answers to a too-early refresh (status and body). Every 4xx other than a clear invalid_grant or client rejection, every redirect, a 2xx that carries an OAuth `error` instead of tokens, a 2xx we cannot parse, and every body we cannot classify is treated as retryable: tokens and status are kept, the authority retries twice after 5 s and 15 s (three attempts, each with a 20 s timeout, so one refresh holds the authority for at most about 80 s), then falls back to the still-valid access token (cooldown 10 s before the next attempt) or answers a retryable 503 `token_refresh_retry`. Only invalid_grant wipes the tokens and sets `needs_reauth`. invalid_grant means the OAuth `error` member equals `invalid_grant` after trimming and lower-casing, at any 4xx status (400 and 401 alike); a text that only appears in `error_description` is ambiguous and keeps the tokens. A 2xx we cannot parse no longer wipes the tokens either (it did before review G2): if the old refresh token was in fact spent, the next attempt answers invalid_grant and that marks `needs_reauth` then. If Exact's too-early answer is in fact `invalid_grant`, this rule would wrongly wipe tokens: check on the live connection (checklist item 1).
18. **Minute limit window (UNKNOWN).** Whether Exact's per-minute limit is a rolling window or a fixed clock minute is unknown. The gate enforces the stricter reading: a sliding-window log, never more than 60 calls in any 60 s (review S1). The log (at most 60 timestamps) is part of the limiter state written to DO storage before each call is sent, so an eviction or redeploy does not reset it. `X-RateLimit-Minutely-Remaining` can only tighten it for the reported reset time.
19. **Rotated tokens and a failing D1.** After a refresh the new pair is written to D1 (two attempts). If both fail, the encrypted pair is kept in the authority's Durable Object storage (`pending:<id>`, ciphertext only, same AAD as in D1, plus the refresh token D1 still holds as the write guard), used from there, and written to D1 by the next refresh request or by the alarm every 30 s until it succeeds. The write is guarded by `refresh_token_enc = <the old value>`, so a stash can never overwrite a newer pair (a re-authorisation) and is dropped when the guard no longer matches or the connection is no longer active. While a stash exists the authority never reads the token pair from D1. The authority shares its one Durable Object alarm with the usage flush through a helper that only moves the alarm earlier, and the alarm writes the stash before the usage flush, so neither use can delay or starve the other. This replaces the earlier rule that a failed write set `needs_reauth` (the old refresh token is dead after rotation, so that forced a needless re-authorisation). If DO storage also fails, `needs_reauth` still applies. Bookkeeping after the pair is safe (issue-time record, clearing an old stash) can fail without touching the tokens.
20. **Rejected client credentials (body UNKNOWN).** `invalid_client` or `unauthorized_client` in the `error` member, or a 401 without invalid_grant, is counted as a client rejection (a wrong `EXACT_CLIENT_ID` or `EXACT_CLIENT_SECRET`, most likely). Tokens are never touched. After 3 consecutive rejections spanning at least 60 s, the authority sets `connections.last_error = 'token_endpoint_rejected_credentials'` (status stays `active`) with one audit row `connection.exact_credentials_rejected` (actor `system`), answers 503 `token_endpoint_rejected_credentials`, and leaves the token endpoint alone for 60 s at a time. `GET /api/connections` returns it as `lastError` and Settings, Connections shows "Configuration problem: Exact rejected the app credentials. Check EXACT_CLIENT_ID and EXACT_CLIENT_SECRET." with no Re-authorise button (re-authorising cannot fix a server setting). The next successful refresh clears `last_error` and the counter. If Exact answers a premature refresh with a 401, the 60 s span keeps that from being mistaken for a credentials problem (the token is old enough by then).

## Live connection checklist (add to ADR 0017 / DEPLOY.md verification)
1. Refresh at age 540 s (should be rejected or refused by us), at 570 s and at 580 s; record Exact's answer (status, body) to the early attempt. Confirm `expires_in` is 600.
2. Confirm that a 401 on a young token does not happen in normal use; if it does, find out why.
3. Provoke `invalid_grant` (revoke the app grant in My Exact Online) and confirm the body is `{"error":"invalid_grant"}` and that `needs_reauth` is then set once, with one audit row.
4. Confirm the refresh token rotates and that its lifetime is about 30 days.
5. Under load for one full minute, check whether the minute limit is rolling or clock-aligned, and what `X-RateLimit-Minutely-*` report.
6. Confirm DO objects show jurisdiction EU (ADR 0018).
7. Use a wrong client secret once on a test deployment: record the status and body, and confirm the Connections screen shows the configuration problem after about a minute while the tokens stay.
8. `/current/Me` returns `DivisionCustomer` (a GUID) and `DivisionCustomerName`; `system/Divisions` accepts `$select=Currency` and returns an ISO code. A 400 on either call names the wrong field.
9. Connect with a second Exact account on a throwaway deployment: the callback must answer `?exact=different_exact_account` and leave the old divisions alone; with the confirmation link the old divisions must be switched off (ADR 0019).
10. Whether `/current/Me` is cheap and allowed right after the code exchange (the callback makes exactly one such call).
