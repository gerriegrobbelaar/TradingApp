# 0035 FX decimal arithmetic (Phase 6)

Status: accepted. Code: `packages/core/src/{decimal,fx,ecb}.ts`.

- **No decimal library.** FX here needs only exact scaling, multiplication, one division and comparison. A 100-line BigInt module (`decimal.ts`: parse, multiply, compare, divide with rounding, toString) is auditable in one sitting, adds no supply-chain exposure, no Workers bundle weight and no float. Rejected: decimal.js / big.js (more surface than we use, another dependency to track).
- **Representation.** Money is integer minor units (`bigint` with |a| < 10^30, else `bad_amount`; `number` accepted only when a safe integer, else `unsafe_number`). A rate is a plain decimal string, "units of the currency per 1 EUR" (ECB convention), at most 12 integer digits (after leading zeros) and 12 fraction digits (before trailing zeros), > 0, ASCII digits only, no sign, exponent or whitespace. `01.50` is normalised to `1.5` and normalising again is a no-op; `.5`, `5.`, `1e5`, `+1`, `1,5`, Arabic-Indic or full-width digits are rejected. Input over 64 characters is refused before any regex runs, so parsing is O(1) on hostile fields (review F1: a trailing-zero regex on the raw fraction was quadratic, a 5 MB OBS_VALUE would have hung the import). `parseDecimal` refuses more than 60 digits. The ECB publishes about 4 significant decimals (USD 4 dp, JPY/IDR 2 dp); 12 is headroom, not precision we claim.
- **Cross rates via EUR.** from -> to = `r_to / r_from`, EUR being 1. So USD -> EUR is amount / r_usd, EUR -> USD is amount * r_usd, X -> Y is amount / r_x * r_y. The amount is converted as one exact rational: `a * 10^scale_to * r_to / (10^scale_from * r_from)`, with the rates as integers over powers of ten. No intermediate rounding.
- **Rounding rule (the only one).** Round half away from zero, once, at the end, to the target currency's minor unit (`currencyScale`: JPY 0, EUR 2, KWD/BHD 3). So `convert(-a) = -convert(a)`, and 0.005 becomes 0.01. Same currency in and out returns the amount unchanged and needs no rate.
- **Displayed rate.** `rateUsed` and `crossRate` are the from -> to multiplier rounded half away to 12 dp with trailing zeros removed. It is for display and audit only; the amount is never recomputed from it. If the multiplier would round to 0 (below 5e-13, no real ECB pair comes near), `crossRate` is null and `convertMinor` returns `rate_out_of_range` rather than recording a rate of 0. `formatRateForDisplay` rounds the same way to 6 dp by default.
- **Unrealised difference** = value at today's table minus the base-currency amount booked, in base minor units. Amounts are signed as in `open_items` (ADR 0022): `open_minor` / `open_dc_minor` are positive for an open invoice (receivable) and for an open bill (payable) alike, and negative for a credit note of either kind. So `differenceMinor` > 0 means the item is worth more in the base currency today. It is not a gain/loss sign: `unrealisedResultMinor(kind, diff)` gives the result (invoice: +diff, bill: -diff). Examples, base EUR: a receivable of +100 USD booked at 90 EUR and worth 92 EUR today has difference +2 and a gain of +2. A bill of +90 USD booked at 90 EUR and worth 100 EUR today has difference +10, a loss of -10. A sales credit note of -90 USD booked at -90 EUR, now -100 EUR, has difference -10, a loss of -10 (we refund more euros); a purchase credit note with the same figures is a gain of +10.
- **Implied booked rate** = booked / open in major units, 12 dp: base-currency units per 1 unit of the item currency, i.e. the direction of `rateUsed` for currency -> base and the inverse of the ECB direction when the base is EUR (USD booked at 0.9 EUR per USD, while the ECB writes 1.1111 USD per EUR). Null when the open amount is 0, the booked amount is 0, their signs differ, or it rounds to 0.
- **Who uses it.** The ECB import job and FX API (Phase 6, F2), live EUR amounts in the UI, matching of foreign-currency payments (Phase 7) and the cash forecast use `convertMinor` and `unrealisedDifference`.
- **Booking (Phase 12)** uses the same functions and the same rule for the month-end revaluation: each open item and balance is converted once from its own amount at the month-end table; differences are summed per ledger account after rounding each item, so the journal equals what the UI shows item by item. Any change of rule needs a new ADR.
- **ECB data.** `parseEcbCsv` accepts SDMX-CSV only, finds columns by header name, skips (and counts) rows with a bad code, date or rate, an empty observation, a denominator other than EUR or a type other than SP00, refuses input over 5 MiB measured in UTF-8 bytes (`ECB_MAX_CSV_BYTES`; `ECB_MAX_CSV_CHARS` remains as an alias), skips rows over 8 KiB, rejects a required column that appears twice (`ambiguous_columns`), checks FREQ = D and EXR_SUFFIX = A when those columns are present, accepts BOM, CRLF/LF/CR, quoted commas and newlines, and never throws. One linear pass (slices, no per-character concatenation): 5 MB of tiny rows parse in about 0.1-0.2 s (a test asserts under 1 s). `buildRateTable` takes the latest observation per currency on or before a date, so a Monday before 16:00 CET uses Friday's rates (`asOf` = Friday) and `ratesDate` keeps each currency's own date. `buildRateTable` also leaves out any currency whose latest observation is more than 10 TARGET working days older than `asOf` (`maxAgeTargetDays`, 0-260): currencies the ECB stopped publishing (HRK after 2022-12-30, RUB after 2022-03-01) must read as `missing_rate`, not as a current rate. Whether `asOf` itself is too old is the caller's alert (CLAUDE.md 3). `ecbRequestUrl` can only produce `https://data-api.ecb.europa.eu/service/data/EXR/D..EUR.SP00.A` with the ECB Data Portal (SDMX REST) parameters `format=csvdata`, `startPeriod`, `endPeriod` and `lastNObservations` (1-1000), and strictly validated dates.
- **Open:** ECB rates are "for information only"; the accountant must still confirm them as the revaluation source (open decision 4).
- **Tests.** Besides unit tests, `fx.oracle.test.ts` checks `convertMinor`, `crossRate` and `unrealisedDifference` against an independent rational implementation (no shared code, a different rounding algorithm) over about 8,000 seeded cases, all scales (JPY 0, EUR 2, KWD/BHD/OMR/JOD 3, CLF 4), signs, amounts up to 10^28 and rates from 1e-12 to 1e12. It also checks exact half-unit ties and the double-conversion drift bound.
