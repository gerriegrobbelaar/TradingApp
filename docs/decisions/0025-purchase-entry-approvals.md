# 0025 Purchase-entry approval status: sync and read API (Phase 4, task K4)

Status: accepted for the code, **provisional for every Exact name, filter and status code below: verify with credentials.** Nothing here has run against a real Exact division; it is tested against a scripted transport. Code: `packages/exact/src/client.ts` (`listPurchaseEntriesChunk`, `purchaseEntryFilterExpr`), `packages/core/src/approvals.ts`, `apps/worker/src/exact/purchase-sync.ts`, `apps/worker/migrations/0011_purchase_entries.sql`, `apps/worker/src/read/approvals-routes.ts`. It follows 0017 (sync design), 0022 (read model) and 0024 (ledger sync, whose pass pattern it reuses).

## What it is for

The Approvals screen (`GET /api/approvals`) and Phase 9's pre-check "invoice approved in Exact" (CLAUDE.md 4.3), and the data quality rule "approvals > 3 days" (4.6). Exact stays the system of record: `purchase_entries` is a cache.

## The status mapping: VERIFY WITH CREDENTIALS (the whole table)

One table, `PURCHASE_ENTRY_STATUS_TABLE` in `packages/core/src/approvals.ts`. Nothing else looks at raw codes.

| Exact `Status` | ApprovalStatus | Basis |
|---|---|---|
| 5 | `pending_approval` | the reviewer's recollection, not verified |
| 50 | `approved` | recollection ("processed / final"), not verified |
| anything else, missing, not an integer | `unknown` | by rule |

No code maps to `rejected` yet: it is a status the API can carry, but no known code produces it, so a rejected entry shows as `unknown` until the table is filled in. That is deliberate. Safety rules, tested:

- an unlisted code is `unknown`, never `approved`; the column default is `unknown`, and the table has `CHECK (status <> 'approved' OR status_code IS NOT NULL)` (migration 0011), so no default, no row without a code and no API fallback can store `approved`;
- `isInvoiceApprovedForPayment(entry, { nowMs, maxAgeMs? })` (core) is true **only** when all of these hold (review K4): the stored status is `approved`; the raw `statusCode` maps to `approved` under the **current** table (a stale derivation or a code later removed from the table does not count); the row was last seen by a read (`synced_at`) at most `maxAgeMs` ago, default and upper bound `APPROVAL_MAX_AGE_MS` = 36 hours (every row in the read's scope is refreshed nightly, so an older stamp means the reads are failing or the entry left the scope and is no longer refreshed), and not more than 5 minutes in the future; and `missed_cycles` is 0 (the last complete read saw it). Anything missing or unparsable is false;
- a wrong guess towards `pending_approval` or `rejected` can only stop a payment, never allow one. **The `approved` row (50) is the one that can allow a payment, so it must be checked first.**

**Phase 9 MUST NOT enable the Pay button (or any pre-check that relies on `isInvoiceApprovedForPayment`) until the mapping has been verified on a real division and the result recorded here.** How: as an admin, `GET /api/approvals/status-codes?division=<id>` lists the cached entries per raw `Status` code with the stored status, the status the current table maps it to, the count and the last time one was seen (counts only, no names or amounts; admin only; a read, not audited). Open entries of every code in Exact's UI and compare (DEPLOY.md step 10, item 16). Correcting the table is a one-line change; the payment helper applies it at once (it re-derives from the raw code), the stored `status` (lists, counts) is re-derived by the next read of each row; rows outside the 120-day window keep the old derivation until they are modified, so after a correction run a full sync with `restart`, or re-derive from `status_code` in a migration. Even with a verified table Phase 9 must re-read the entry from Exact when it prepares a payment: the cache can be an hour old, and an approved entry older than the window is not refreshed at all (the helper then says false, which is the safe answer, not the final one).

## Verify with credentials (everything else)

1. **Resource:** `purchaseentry/PurchaseEntries` (candidates were also `PurchaseEntries` in other services). A 400, 403 or 404 on the first page marks the entity unavailable for a day (`sync_state.unavailable_until`, `last_error = purchase_entries_unavailable_<status>`); the API answers `available: false`. Our own gate's 400 codes never mark it. `restart` on a manual full sync tries again at once.
2. **Fields** (`PURCHASE_ENTRY_FIELDS`): `EntryID, EntryNumber, Supplier, SupplierName, Currency, AmountFC, AmountDC, EntryDate, DueDate, Status, Created, Modified, Document`. A wrong `$select` name is a 400 and shows as unavailable. `DueDate` may not exist on the header (it may be `PaymentCondition` plus lines): then `due_date` is null. `Created` is taken as the submission time (`submittedAt`); if Exact has a better field (the date it entered the approval flow), use it.
3. **Filters:** `$filter` with `or` between `EntryDate ge datetime'...'`, `Modified ge datetime'...'` and `Status eq 5`, and `$orderby=Modified`. UNVERIFIED that `Modified` is filterable and sortable, that **every status change updates `Modified`** (the hourly read and the tracking of a pending entry older than the window depend on it; if not, such an entry is dropped by the next complete read, never kept as approved), and that `$skiptoken` stays valid between runs (same assumption as ADR 0017 item 10).
3a. **Time zone (flag).** We read `/Date(ms)/` values and write `datetime'...'` literals as UTC. Exact may use Amsterdam wall-clock time instead. The hourly cursor is built from Exact's own `Modified` values and sent back in the same frame, so it is consistent either way; the first cursor (our clock minus 10 minutes) and the window start would then be 1 to 2 hours early, which reads a little more (safe). A Modified that is ahead of our clock moves the cursor at most to now + 3 hours (`CURSOR_FUTURE_LIMIT_MS`), above that offset. `submittedAt` / `ageDays` could be a day off around midnight. Verify (DEPLOY.md).
4. **`hasPdf`:** from the `Document` field (a GUID means a document is attached). When the row has no `Document` key at all the value is null ("could not tell"). The documents/attachments resource (`documents/DocumentAttachments`) is NOT read: one call per entry is too expensive, and a bulk read of attachments is unverified.
5. **Amounts:** `AmountFC` in `Currency` is the entry total (credit notes negative, assumed); `AmountDC` in the division currency, optional. A missing currency falls back to the division currency.
6. **Dates:** entry and due date are stored as Amsterdam calendar dates (ADR 0017 item 5).

## Scope: which entries are read

An entry is read when its `EntryDate` or `Modified` is within the last **120 days** (`PURCHASE_ENTRY_WINDOW_DAYS`) **or** its status code is one that maps to `pending_approval` (whatever its age). Everything older and not pending is not read and not refreshed, which bounds the volume; the Approvals screen is about recent and open work. An old entry whose status is an unknown code is not read until it is modified within the window. The window start is fixed by the pass start (`pass_started_at`), so a saved `$skiptoken` is always used with the filter that issued it.

## Sync

Entity `purchase_entries`, one `sync_state` row per division like the others. In the FULL order it comes after the IBANs and **before the ledger** (review K4: a large ledger may need several nights, ADR 0024, and must not keep the approvals and the nightly refresh the payment pre-check relies on waiting); in the hourly INCREMENTAL order right after `divisions` (before the relations, whose first walk can use the whole hourly budget). `readPurchaseEntries: false` switches it off. Every write of the entity, the row upserts included, is guarded by the sync lease: a run that outlived its lease writes nothing (tested for the full read, the close and the hourly read).

- **FULL:** a resumable pass (the ledger pattern): each chunk of 5 pages writes its rows, the saved `$skiptoken`, the row count and the pass start in one D1 batch, guarded by the sync lease (a run that outlived its lease writes nothing). Resumed in later runs of the same cycle. Only a COMPLETE read removes anything: rows in the read's scope that the pass did not see (`last_seen_sync_id < pass seq`, scope = the same three conditions as the filter) get a strike and are deleted after **two** complete reads in a row, or one when the pass ran inside a single run (no token carried over) or an admin passed `allowLargeClose`. Close guard: more than max(5, 20 %) of the scope at once is refused (`close_guard`, nothing changes). A complete answer with no row at all while we hold rows changes nothing (`empty_answer_ignored`) and does not start the cursor. Rows outside the scope are never removed. Strike, delete and cursor start are one D1 batch under the lease.
- **INCREMENTAL (hourly):** `Modified ge <cursor>` ordered by Modified, cursor in `sync_state.cursor` (epoch milliseconds; that column only holds digits, migration 0005). `ge` so a tie at the cursor is read again (the literal is truncated to the second, which only reads more); upserts are idempotent. The cursor starts when the first complete full read ends (pass start minus 10 minutes, `CURSOR_MARGIN_MS`, for clock skew) and moves forward after the rows up to it are written, and only when the chunk was in ascending Modified order (otherwise it stays: fail-safe). It never moves back: the hourly update and every later complete full read take the larger value (a complete pass moves it to its own start minus the margin: every change after that instant is inside the window and so either read by the pass or by the hourly read from there; this also frees a cursor the hourly cap cannot move, more same-second changes than two chunks). Only an explicit `restart` sets it back (re-reads). After the first cursor there is no overlap beyond the tie: a change committed in Exact with a `Modified` earlier than one already read (late commit) is missed by the hourly read and caught by the next nightly pass (in-window and pending entries only). Before that first complete read the hourly run does nothing for this entity (`skipped`/`no_cursor`) and the API says `available: false`. Never deletes, never inserts old history (a row is only upserted when Exact returned it).
- **Cap:** at most `INCREMENTAL_MAX_CHUNKS` (2) chunks = 10 calls per hourly run, so an import of hundreds of entries cannot take the hour's 40. A capped run ends `skipped`/`incremental_cap` for this entity: the cursor is saved, the next hour continues, the run stays `ok`, and `last_completed_at` is not touched, so the API does not claim the data is current while a backlog is worked off.
- **Errors** as for the other entities: budget, rate limit, deadline and subrequest stops are `partial`; an unexpected API error is `error` for the entity and the saved token is dropped.

## Call arithmetic

The job budgets are unchanged (240 per full attempt, 40 per hourly run), so the scheduled worst case per administration and day is still **4 x 240 + 25 x 40 = 1,960** of 5,000 (`test/purchase-budget.test.ts` recomputes it from the constants, and `jobs-exact.test.ts` still asserts 1,960). What changes is how a night's budget is shared: a window of 640 entries is `ceil(640 / 60) = 11` calls, which with the reference division's 153 calls for the other entities (50 + 34 open-item pages, 67 IBAN pages, 2 for divisions and relations) and 65 for the ledger (ADR 0024) is 229 of 240, still one attempt (234 with an opening row for every account); the weekly ledger night was already 308 and is now 319, a second attempt as before. A busy administration (6,000 entries in 120 days) is 100 calls: as the entity now runs before the ledger, it is 253 calls before the ledger, so the first attempt stops partway through the purchase pass, the second resumes it from the saved token and then reads the ledger, which the scheduler gives (4 attempts). The hourly read is usually one call (the changes of the last hour); worst case 10 (the cap), of the 40.

## Table and API

- `purchase_entries` (migration 0011): see the file for columns. `status_code` raw, `status` derived, `has_pdf` nullable, `search_text` (folded entry number and supplier name), `last_seen_sync_id` and `missed_cycles` as for open items. Additive migration, tested on a populated database.
- `GET /api/approvals?division=&status=&q=&limit=&cursor=` and `GET /api/approvals/:id`. Any signed-in role. `status` defaults to `pending_approval` (also `approved`, `rejected`, `all`; `unknown` cannot be asked for and shows under `all` and in `countsByStatus`). Order: pending oldest first, anything else newest first, ties by id, keyset cursor bound to its direction. `countsByStatus` follows `q` but not `status`. `ageDays` (pending only) = Amsterdam calendar days since `submittedAt`, else since the entry date. `freshness` has basis `purchase_entries` and the 36-hour stale rule of 0022. `available` is false until the entity has completed once (also when Exact refused the resource from the start); a later refusal or failing reads keep the cached rows visible with `freshness.stale` after 36 hours, and the error in `GET /api/sync/status` (`last_error`). `GET /api/approvals/status-codes` (admin only) is described above. The `relation` is the supplier name as read with the entry, else the synced relation's name; its `id` links to `/api/relations/:id`. No IBAN, email or VAT number is stored in the table or returned (tested). Types: `ApprovalItemDto`, `ApprovalsResponse`, `ApprovalDetail` in `packages/core/src/api-types.ts` (the first two are the fixed interface agreed with K3a; `FreshnessEntity` gained `purchase_entries`).
