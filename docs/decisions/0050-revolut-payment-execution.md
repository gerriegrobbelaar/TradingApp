# 0050 Revolut payment execution, reconciliation and the payment gate (Phase 9, P9b)

Status: accepted for P9b. **NOTHING HERE HAS RUN AGAINST A REAL REVOLUT.** The code ships with every switch OFF; the verification (below) is explicit and is the reason the A-items exist. Code: `packages/revolut/src/payments.ts` (builders, parsers, classification), `apps/worker/src/revolut/{request,gate,wire}.ts`, `apps/worker/src/payments/{gate-flag,protocol-version,revolut-submitter,payees,submit,reconcile,reconcile-job,preview,tx-match}.ts`, migration 0029, `packages/core/src/payments/runbook.ts`.

## What P9b builds

The real `PaymentSubmitter` (counterparty once per supplier IBAN, then `/pay` or a payment draft), the payment surface of the Revolut gate, a per-connection payment lease and send ledger, the reconciliation job, the link between a paid payment and its bank line, the verification checklist with its runbook, the admin "Preview payment" dry run, and the typed "this unknown payment was not sent" resolution. It does not build the web screens (P9c), reminders, or the booking of a paid invoice in Exact (the standard matching and booking path does that, ADR 0044).

## The gate surface (ADR 0048 invariants hold)

`revolut/request.ts` opens exactly five entries and nothing else:

| Entry                      | Kind  | Needs                                                                                                                 |
| -------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------- |
| `POST /counterparty`       | write | payment job class, `user` priority, lease, ledger key `cp-…`, body keys `company_name, bank_country, currency, iban`  |
| `POST /pay`                | write | same; body keys `request_id, account_id, receiver, amount, currency, reference`, `request_id` equal to the ledger key |
| `POST /payment-drafts`     | write | same; body keys `title, payments`, `title` equal to `CF-` + 12 hex of the ledger key                                  |
| `GET /payment-drafts`      | read  | payment job class                                                                                                     |
| `GET /payment-drafts/{id}` | read  | payment job class                                                                                                     |

The job class is `revolut-payment` or `revolut-payment:<suffix>` (`revolut-payment:reconcile` for the job). `GET /transaction/{id}` was already open to every job (transactions are read by the sync); the lookup by `request_id` uses it. No `DELETE`, `PUT`, `PATCH`, `/transfer`, `/exchange` or bulk endpoint exists. A lease or ledger key on anything but a payment write is refused (so it cannot ride on a webhook or a read).

**Reads are NOT behind the D1 switch**: switching payments off must never blind the reconciliation of what is already in flight. Writes are: the gate reads `payments.enabled`, the mark and the deploy var itself at the door and again immediately before the network call (invariant 3).

**Payment lease** (`acquirePaymentLease` / `releasePaymentLease`, Durable Object RPC): a mutex per Revolut connection with a 5-minute expiry, held in memory and storage, check-and-set without an `await` in between. `submitPayment` takes it before `runSubmission` and gives it back after; a second submission gets `busy` and its request stays `ready` (nothing claimed). Everything that must not race (pre-checks including the daily ceiling and the balance reservation, the claim, the calls, the write of the result) therefore happens for one request at a time. The gate additionally refuses any payment write whose lease token is not the current, unexpired one (checked at the door and right before the fetch), so an expired holder cannot send. The three RPC methods return no token and send nothing (`gate-rpc-surface.test.ts` pins the prototype list).

**Send ledger** (`paysend:<ledger key>` in Durable Object storage, 60-day retention): written BEFORE the fetch, so "never attempted" is proof that the instruction did not leave the gate. A ledger key can be used once: the gate itself refuses a second payment write for the same key (`payment_already_attempted`, 409), even with a valid lease and an identical body. `paymentSendState(ref)` answers `never_attempted` / `attempted`.

**The 401 rule** (G9 invariant 2, unchanged): a 401 on a write heals the token and fails with the typed `RevolutWriteAuthRetryRefused` (own wire kind `write_auth_retry_refused`, a `RevolutApiError` 503 so every existing caller keeps working; distinct from `gate_unavailable`, which means the gate was reset and nothing is known). Task text item 1 calls it "definitely not executed"; item 3 says a 401 on a payment is definite only if the gate says it never sent. Both hold: **the payment classifier treats a 401 after an attempt as `unknown`** (the request was sent, a 401 should mean "not executed" but that is an A-item) and the reconciliation settles it by lookup. Webhook and DELETE callers keep their one retry.

## The submitter

`createRevolutSubmitter` is built per submission with the lease. In order:

1. Refuses before any call: a batch in `pay` mode (`batch_pay_unsupported`: Revolut's `/pay` is one payment; bulk goes through drafts), `pay` on a connection that is not on the Company plan (`mode_not_allowed`), IBAN or key problems (`iban_binding_broken`), a payload that disagrees with the stored rows (`payload_mismatch`). All are `rejected`; nothing was sent.
2. **Payee**: per (connection, IBAN fingerprint) one Revolut counterparty, cached in `payment_payees`. The name and IBAN come from the request row (copied from the verified supplier record at creation), re-checked against the approved fingerprint in `readSendTargets` (the only full-IBAN reader for sending, `iban-store.ts`); never from request input. An idempotency key (`revolut.payee`) is stored before creating; an existing one makes it look in `GET /counterparties` for the IBAN first. The answer must echo exactly our IBAN or the payment fails closed (`counterparty_iban_unconfirmed`). A failure at this stage is `rejected` because no payment was sent.
3. **Idempotency key** (`revolut.pay` / `revolut.draft`, key = the request id) stored BEFORE the payment call (ADR 0013). A key that already exists means an earlier attempt began: nothing is sent, the answer is `unknown`.
4. ONE call: `/pay` with the STORED `request_id` (never generated here), or one `/payment-drafts` (a bulk draft for a batch). Never retried, never with a new id. The whole submitter is bounded by 150 s (the gate lease is 5 min, the claim lease 10 min); a timeout is `unknown`.
5. A failure is sorted by `classifyPaymentFailure(error, ledger)`:
   - local validation error or **ledger `never_attempted`** → `not_executed` → `rejected`;
   - 409 → `duplicate_request_id` → look up and adopt;
   - 429 after an attempt → `rejected rate_limited`; 400/403/404/422 → `rejected(code)`;
   - 401 / refused-after-401 / 5xx / network / timeout / `gate_unavailable` / an unreadable 2xx / anything else → `unknown`.
     Before a `/pay` is called `rejected`, the request id is looked up: a transaction that is exactly ours (amount, currency, source account; `transactionMatchesPayment`) is ADOPTED (`submitted`, or `rejected` if its state is declined/failed). An `unknown` is also looked up once and adopted if found. A drafts failure is looked up by its title in the draft list. A transaction under our id with other content is never adopted (reported by the reconciliation).
6. Outcome mapping to P9a: accepted → `submitted` (provider id = transaction id or draft id), rejected → `rejected`, unknown → `outcome_unknown`. `runSubmission` stays the single call site (`submitPayment` in `submit.ts`, called from the submit routes only; scans pin both).

## Reconciliation (`payments.reconcile`, every 5 minutes, enabled, inert)

For every `submitted` / `outcome_unknown` payment or batch, READ-ONLY through the gate (job class `revolut-payment:reconcile`, budget 120 calls): by `request_id` (pay) or by draft id / title (drafts). Rules: only FINAL bank states move a payment (`completed` → `paid`; `failed`, `declined`, `reverted` → `failed`; `pending` leaves `submitted` and lifts `outcome_unknown` to `submitted`); a found transaction must be ours; **not found never moves anything** (it is counted); lookup errors are recorded; nothing is ever sent or retried. With nothing in flight no client is created and no call is made (tested). It runs with payments switched OFF. A draft not approved after `payments.draft_expiry_days` (1..30, default 5; `PUT /api/settings/payments/draft-expiry`) becomes `failed` / `draft_expired`; an expired draft stays on a 30-day watch and an approval after the expiry is raised once (`approved_after_expiry`, audit row), because the draft still exists in the Revolut app and could be paid while the invoice looks unpaid here (a person must delete it in the app; see questions).

**Paid and booked (CLAUDE.md 4.3).** `paid` in `payments.status` is the bank's word (ADR 0049); a trigger-guarded, append-only `payment_bank_links` row ties the payment to the bank line (same account, currency, amount, money out) by request id or transaction id; no second bank entry is ever created. `paymentSettlement` (and `GET /api/payments/:id/settlement`) says how far the second fact is: `awaiting_bank_line` → `awaiting_match` → `awaiting_booking` → `booked` (a live match for that line allocates THIS invoice and is `matched_in_exact`), or `match_other_invoice`. The standard matching engine matches the line (reference `Invoice <number>` and the exact amount are rule 1); the UI must show "Paid" only for `booked` and "Paid at the bank, booking pending" otherwise. A bank line that later turns reverted/failed/declined for a paid payment is raised once (`reverted_after_paid`). No new status was added: a final `paid` cannot be updated (0028), so the second fact lives in its own tables (migration 0029).

**Resolving an unknown by hand.** `POST /api/payments/:id/resolve-not-sent` (and batches): admin, fresh sign-in, phrase `MARK PAYMENT AS NOT SENT`, and only if the last lookup said "not found" less than 30 minutes ago and the call began at least 15 minutes ago. The database refuses `outcome_unknown → rejected` unless a lookup found nothing (`payments_guard_unknown_reject`). Wrong = a possible double payment, which is why the phrase says so.

## Assumptions, all UNVERIFIED (the A-items; the checklist closes them)

Written from memory of the public Business API documentation. Each is also flagged `A-ITEM` in the source. Replace the fixtures in `packages/revolut/test/payment-fixtures.ts` with sandbox recordings; a difference is the finding.

- **A1** `POST /counterparty` takes `company_name`, `bank_country`, `currency`, `iban` (no BIC, no `profile_type`) and answers `{id, name, accounts:[{id, iban, ...}]}` including the IBAN. A payee answer without our IBAN is refused (fail closed). Whether Revolut de-duplicates a repeated counterparty, or masks the IBAN, is unknown. (`sandbox_counterparty_roundtrip`)
- **A2** `POST /pay` body: `request_id, account_id, receiver{counterparty_id[, account_id]}, amount, currency, reference`; no `transfer_reason_code`, `charge_bearer` or `schedule_for` is sent (so EUR/SEPA only by default; other corridors may need a transfer reason). Answer `{id, state, created_at, completed_at?, reason_code?}`. (`sandbox_pay_roundtrip`)
- **A3** `amount` is accepted as a JSON NUMBER with exactly the currency's decimals ("amount":1234.50), written as a raw token by one audited function (`revolutAmount`), never through a float. (`amount_format_probe`)
- **A4** `reference` up to 140 characters and the SEPA character set (the app already sanitises to it). The real limit may be lower. (`reference_charset_probe`)
- **A5** A repeated `request_id` is refused (we assume HTTP 409) or answered with the original; the body `code` vocabulary is unknown, so classification uses the status only. Our UUIDv4 is accepted as `request_id`. (`request_id_idempotency_replay`)
- **A6** `GET /transaction/{request_id}?id_type=request_id` returns the transaction with `request_id`, `legs[].account_id`, a negative `legs[].amount` for money out, and answers 404 when there is none. A transaction can appear a little after the call. (`lost_answer_lookup_drill`)
- **A7** `POST /payment-drafts` takes `title` and `payments[]` (one entry per payment, several = a bulk draft) and answers `{id}`. **It has no per-payment `request_id`**, so a draft is not idempotent: the title `CF-<12 hex of our request id>` is our marker, and a lost answer is resolved by listing drafts. A title length limit is unknown. (`sandbox_draft_roundtrip`)
- **A8** `GET /payment-drafts/{id}` and `GET /payment-drafts` exist and show `title`, a state and `payments[{state, transaction_id?}]`; the list is a bare array or `{payment_drafts:[...]}` and fits one page. Only the state `completed` counts as done; `failed, declined, revoked, cancelled, canceled, rejected, reverted, deleted` count as refused; anything else is pending.
- **A9** An approved draft executes the payments, producing transactions that arrive as bank lines (webhook/sync). An unapproved draft stays pending indefinitely; there is no server-side expiry we rely on.
- **A10** Statuses: 400, 403, 404, 422 are refusals of THIS request; 429 is "not processed"; 5xx and network errors say nothing about execution.
- **A11** `/pay` on a plan without it answers a 4xx (treated as `rejected(code)`); the plan is not detectable by API, only the connection's `payments_mode` hint.
- **A12** Transaction states are `pending, completed, declined, failed, reverted` (as ADR 0030); only the last four are final; a `completed` can later be `reverted`.
- **A13** The Revolut webhook/sync stores payments we initiate with `request_id` (ingest, ADR 0033) so the link by request id works; for drafts the link goes by transaction id from the draft view. (`webhook_state_sequence`)
- **A14** `GET /counterparties` returns each counterparty's accounts with IBANs (used to find a payee after a lost answer).
- **A15** A 401 on a write means Revolut did not execute it. We do not rely on it: it is `unknown`.
- **A16** The per-minute limit is 60 (ADR 0031); a payment costs one call.
- **A17** The source `account_id` is the Revolut account uuid stored as `bank_accounts.external_id`.

## Deviations from the task text

- `payments.enabled` is the JSON value `true` (the one stored form: the P9a triggers read `'true'`), not `'1'`.
- Added a DEPLOY-level switch (Workers var `REVOLUT_PAYMENTS_EXECUTION`, default `"off"`): without it the enable path would be circular (the P9a blocker `submitter_unavailable` needs a submitter that exists before the D1 switch is on) and "ships OFF" would rest on one setting.
- The wire kind `write_auth_retry_refused` carries no `sent` flag; "did the gate send?" is answered by the send ledger (written before the fetch), which also covers a Durable Object restart. A 401 on a payment is `unknown` (not definite), see above.
- A draft not approved in time ends `failed` (`draft_expired`), not `expired` (P9a's `expired` means "not sent within 24 h" and `submitted → expired` is not a legal move).
- Batches are drafts only. A batch in `pay` mode is rejected before any call; Revolut's `/pay` is one payment and N separate payments would need per-item outcome states that P9a does not have.
- `paid` stays the bank's word; the booked state is `paymentSettlement`, not a new status (a final row cannot be updated).
- The reconciliation does not call an unknown payment "not sent" by itself, ever. Only a person can (see above).

## Consequences

- Money can move only if: the deploy var is `"on"`, the admin enabled payments with the phrase after a complete verification at the current version, a finance user clicks send with a fresh sign-in, every P9a layer holds, the gate lease and its own D1 read agree, and the ledger key was unused. Any one missing is a refusal with a stable code and no call.
- The send ledger and idempotency keys make "at most one attempt per request id" a property of the gate, not of the caller; the price is that a lost answer is never resolved by trying again, only by looking.
- Drafts are not idempotent at Revolut (A7). The title marker and the draft list are the mitigation; the residual risk is a duplicate draft that a person approves twice. The reconciliation raises two drafts with one title.
