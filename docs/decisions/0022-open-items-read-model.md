# 0022 Open items read model (Phase 4)

Status: accepted. Code: `packages/core/src/{ageing,kpis,search,api-types}.ts`, `apps/worker/src/read/`.

- **What totals mean.** Every figure is the sum of `open_items.open_minor` of rows matching the filters, in integer minor units. Credit notes are negative and reduce a total. Totals cover all matching rows, not just the page.
- **Per currency, never across.** Lists, ageing and KPIs report each ISO currency separately (`totalsByCurrency`). No FX conversion happens in Phase 4; EUR-equivalents at the ECB rate arrive in Phase 6.
- **Division currency (DC).** `dcMinor` is the stored `open_dc_minor` when its currency is the division currency (or unstated). An item already in the division currency uses its own open balance, but only once the division currency was read from Exact (`currencyVerified`). Otherwise `dcMinor` is null. Sums add the known amounts and carry `dcComplete: false` (with `dcMissing`) when any row lacks one, so a UI must show "incomplete" rather than a total.
- **Ageing basis is the due date**, not the invoice date. Days overdue = `asOf - due` in Amsterdam calendar days; due today is not overdue. Buckets: not due, 1-30, 31-60, 61-90, 90+, and `no_due_date` for unknown dates.
- **`asOf`** is today's Amsterdam calendar date only (the server's clock; omit it and read `asOf` from the response). The tables hold today's balances, so a past date would silently omit items paid since (400 `as_of_in_past`) and a future one would present today's balances as a projection (400 `as_of_in_future`). A true historical ageing needs ledger data from Exact. Drill-down filters carry absolute due dates and no `asOf`, so a drill-down opened after midnight still returns the cell's rows.
- **`stored_minor` caveat (review N4, renamed in S10).** `open_items.stored_minor` (called `amount_minor` until migration 0017) equals the open balance when Exact did not tell us the invoice total. The API therefore exposes `originalMinor` (null when unknown) and never presents `stored_minor` as an invoice total; only the detail endpoint shows it (`storedMinor`, labelled "Amount as stored"). Phase 7 must use `originalMinor`.
- **KPIs.** "Due in 7/30 days" means due from today up to and including today + N (30 includes 7). Average days overdue is weighted by amount, integer math (BigInt), rounded half up, over overdue items with a positive balance. Every figure carries a `drilldown` (list filters that return exactly its items; tested figure by figure).
- **Ageing drill-down.** The per-currency totals carry one hint per bucket; a relation's cell is that hint plus `relationId` (`drilldownForRelation`). Rows carry no hints of their own, which kept the report from growing by seven hints per relation.
- **Lists.** Order is (due date, id), unknown due dates last, keyset cursor (opaque, bound to the sort direction, strictly validated: 400 `bad_cursor`), page size at most 100. Indexes: migration 0009; a test checks the plan with EXPLAIN QUERY PLAN.
- **Text search.** SQLite cannot fold diacritics, so the folded text of invoice number, entry number, relation name (as on the open item) and reference is stored in `open_items.search_text` (migration 0009, `searchText` in core: each field normalised, joined with a line feed so a word never matches across two fields). The sync upsert writes it; a search is then one `LIKE ? ESCAPE '\'` per word (at most 8 words, wildcards escaped) in the same SQL as every other filter, so it pages with the keyset and totals in SQL. Rejected: filtering up to 20,000 rows in code per request (the first version): about 100-150 ms CPU and 20,000 rows read per keystroke, and a hard failure once closed history passed the cap. Rows written before 0009 hold NULL; the first search in a division fills them (one SELECT and one UPDATE per 2,000 rows, at most 10 chunks per request, else 503 `search_index_building` with `Retry-After`). Not covered: the relation's own name when the open item has none (`relation_name` NULL).
- **Freshness.** Based on the last complete read of the open items themselves: `sync_state.last_completed_at` of `receivables` and/or `payables` (`basis`; the Overview uses both and takes the older, the ageing report its own kind). `stale` is true when that is older than 36 hours or missing. Not the `run` row: hourly incremental runs complete without reading open items (ADR 0019), so they would hide a nightly full sync that keeps failing.
- **Privacy.** Lists and details never return IBANs or email addresses; relations expose presence flags only.
- **Exact deep link** is `null`: the URL pattern for opening an entry in Exact is not verified. Verify with credentials, then fill `exactDeepLink()`.
- **Division visibility.** A division is readable when its Exact connection is not disabled (as in the switcher). All signed-in roles see all such divisions.

## Addendum (M2, Phase 4 review S11, N3)

`open_items.stored_minor` is "the amount as stored" (renamed from `amount_minor` by migration 0017, review S10: the old name read like an invoice total, and the other tables keep `amount_minor` for their own amounts) and for rows from the list endpoints may equal the open balance. The guard tests (`apps/worker/test/amount-minor-guard.test.ts`, `apps/web/src/amount-minor-guard.test.ts`) are plain name scans: `stored_minor` / `storedMinor` may appear only in `exact/sync.ts` (the upsert), `read/routes.ts` (the detail route), the item sheet row "Amount as stored" and the type definition in `api-types.ts`. `provenance.source`: `list` = the nightly full read of the open-item lists, `sync` = the hourly incremental read (labels fixed). Migration 0012 changes the default of `connections.creates_bank_entries` to **0** for new rows (existing rows keep their value; FK-safe copy-aside rebuild as in 0004). **Phase 5 must set it explicitly per connection** (open decision 2: whether Revolut's own Exact integration creates the bank entries).
