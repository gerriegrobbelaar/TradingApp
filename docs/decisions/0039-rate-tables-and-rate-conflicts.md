# 0039 Server-side rate tables and ECB rate conflicts
Status: accepted (Phase 6 review S8, S9). Code: `apps/worker/src/fx/{rate-table,conflicts}.ts`, `apps/worker/src/read/fx-routes.ts`, migration `0019_fx_rate_conflicts.sql`.

## Rate tables (S8)
One module builds a core `RateTable` from `fx_rates`, so the rates API, the Phase 8 rule "foreign item without rate" and the Phase 12 revaluation cannot disagree.
- `loadRateTable(db, onOrBefore, {maxAgeTargetDays})`: newest rate per currency on or before the date, with the cut-off of core `buildRateTable` (default 10 TARGET days: a currency the ECB stopped publishing is left out). A Friday rate serves the weekend and Monday, holidays reuse the last rate. The rates API now uses it (`loadRateTableWithNewest`, which also returns the newest stored date for the freshness line); its answers are unchanged.
- `loadRateTableExactly(db, date, required)`: STRICT, for booking. Only rates dated exactly `date`. Errors: `bad_date`; `unresolved_conflict` (any unresolved conflict for that date, with the currencies); `rate_date_mismatch` (nothing stored for that date: the newest on or before it is older, so Friday's rate is NOT served for a Saturday month-end); `missing_rate` (a required currency has no rate that day). EUR is implicit.
- `currenciesWithoutRate(db, currencies, onOrBefore)`: the currencies a conversion on that date could not price (EUR never).
Reads only: an index seek on `rate_date` and an index range.

## Rate conflicts (S9)
The importer never overwrites a stored rate (ADR 0036). When the ECB later shows another value for a stored (currency, date):
- `fx_rate_conflicts` (migration 0019): one row per (currency, date, ECB value), with `stored_rate`, `first_seen_at` and an open/resolved state (`resolved_at`, `resolved_by`, `resolution` `kept|accepted`, all three set together). The importer upserts it in the same batch as its `fx.rate_conflict` audit row (the audit row stays the history); conflicts beyond the per-run audit cap and ones already audited are upserted too. Existing audit rows are copied in unresolved by the migration (only rows whose code is three capital letters, whose date has the date shape and whose `stored` and `ecb` are JSON strings; anything else is skipped without failing the migration). A resolved conflict is not re-opened by the same value; a new ECB value is a new row; the same value comes back as open only if the stored rate has changed since it was resolved (the ECB flipped and the admin accepted in between).
- `GET /api/fx/conflicts[?resolved=1]` (admin, finance): unresolved first, newest date first, at most 200; `unresolvedCount`. `GET /api/fx/rates` carries `unresolvedConflicts` (optional in the type, always sent) for the UI and Phase 8.
- `POST /api/fx/conflicts/:id/resolve` (admin, step-up, CSRF), body `{resolution:'kept'|'accepted', confirm:true}` (`confirm` must be literally true, extra keys refused). `kept` marks it resolved. `accepted` replaces the `fx_rates` row with the ECB value. The audit row (`fx.rate_conflict_resolved`, before and after rate, conflict id), the replacement and the resolved mark are one D1 batch (ADR 0013), each guarded by "still unresolved and the stored rate is still the one read", so all three happen or none. The same resolution again is a 200 with `alreadyResolved: true` and writes nothing; the other resolution is 409 `already_resolved_differently` (two admins deciding at the same time: one wins, the other gets this 409, one audit row); a conflict whose stored rate is gone is 409 `stale_conflict`. The value written by `accepted` is the stored conflict row's ECB value in core `parseRate`'s canonical form, never anything from the request (extra body keys are refused); a row whose ECB value does not parse (only possible for a malformed old audit row) can be kept but not accepted: 409 `bad_conflict_rate`.
- Phase 8: alert on `unresolvedConflicts > 0` (warning). Phase 12: `loadRateTableExactly` refuses the month-end date until every conflict for it is resolved.
- Roles: finance may read but not decide; deciding which rate is right changes booked values and is an admin act with a fresh sign-in. Accepting a changed ECB value is still subject to open decision 4 (the accountant confirms the source).
