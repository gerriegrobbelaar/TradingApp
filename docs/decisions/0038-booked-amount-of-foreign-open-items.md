# 0038 Booked amount of foreign-currency open items
Status: accepted (Phase 6 review B1; reviewed in T1). Code: `apps/worker/src/exact/sync.ts` (`openItemStmt`/`KEEP_DC`, `syncOpenItemsFull`, `withComputedBooked`), migration `0020_open_items_dc_source.sql`, `packages/core/src/fx.ts` (`bookedAtRate`), `packages/exact/src/client.ts` (`OPEN_ITEM_LIST_DC_FIELDS`), `apps/worker/src/exact/sync-routes.ts` (settings).

## Problem
The unrealised FX difference needs the booked amount of an open item in the administration currency: `open_items.open_dc_minor` (with `dc_currency`). Only the incremental sync endpoint (`/sync/Cashflow/*`: `AmountDC`, `RateFC`) carries it, and that read is off by default (ADR 0017, same-ID assumption). The nightly full list pass (`read/financial/ReceivablesList` / `PayablesList`) has no such field in its `$select` and used to overwrite the column with NULL on every item, so the "Booked" line and the difference never showed in a default install.

## Decision
1. **Stop the wipe (always on), one statement, with a source (migration 0020).** `open_items.dc_source` records where the booked amount came from: `sync` (the incremental sync endpoints), `list` (option 1) or `computed` (option 3); NULL with no amount. The upsert decides in ONE SQL statement from the old row (`open_items.*` in `DO UPDATE`, which SQLite evaluates against the pre-update row in every SET expression) and the new values (`excluded.*`): the stored amount, its currency and source are **kept** only when the currency and `open_minor` are unchanged, an amount is stored, and the read carries none or one from a worse source (rank sync 3 > list 2 > computed 1). Otherwise the read's amount is taken, which is NULL when it carries none. So: a changed open amount (part payment, credit, an item closed and reopened: closing sets `open_minor` 0) or a changed currency never keeps a stale amount; a value read from Exact beats a computed one, but only for the same open balance; the same source refreshes its own value. There is no read-modify-write: the incremental and full passes run under the per-division lease anyway. A part payment seen only by the nightly list clears the booked amount of the remainder until a sync read or option 3 gives it again; the UI says "Booked amount not known yet". `original_minor` and `rate` keep their ADR 0017 rule (kept while the currency is unchanged). Existing amounts were all read by the sync endpoints and are marked `sync` by the migration.
2. **Three ways to fill it**, all admin-controlled and verified live before use:
   - **Option 1: list fields.** The documented fields of `ReceivablesList` / `PayablesList` (ADR 0014 item 3) include no division-currency amount and no rate. `AmountDC` and `RateFC` are a guess copied from the sync resource, so they are NOT requested by default. Setting `exact.list_dc_fields` (admin with a sign-in from the last 15 minutes, `PUT /api/sync/settings {listDcFields}`, audited) adds them to the list `$select`. When Exact answers 400 to it (not one of our gate's own 400 codes), the read is repeated once without them; only if that plain read works is the 400 taken to be about the fields and remembered for 7 days on the entity's own `sync_state.unavailable_until` (the `receivables` / `payables` rows; the budget and purchase reads keep their memory on their own entity rows, so the features cannot collide). If the plain read fails too, its error is the run's error and nothing is remembered, so a 400 caused by something else (a bad filter) does not hide the feature for a week. A `restart` run tries the fields again and forgets the memory when they are accepted; changing the setting forgets it too. `GET /api/sync/settings` shows `listDcFieldsUnavailableUntil` so an admin sees that the switch is on but not in use. Switching the setting off clears every `list` amount (they are no longer trusted). Cost: one extra call per list and run while refused, once a week; none otherwise.
   - **Option 2: a cheap bulk read.** Not built: no known endpoint is cheaper than the sync endpoints, which already exist behind the incremental setting. Turning that setting on after the same-ID check (DEPLOY.md item 9) is the way to get `AmountDC` and `RateFC` from Exact itself.
   - **Option 3: open amount times the booked rate.** `exact.rate_direction` = `base_per_foreign` (division-currency units per 1 unit of the item currency, 0.92 for USD in a EUR division) or `foreign_per_base` (the ECB way, 1.087), unset by default. Unset means a booked amount is never computed. When set, for each open foreign-currency item of a list chunk that carries no division-currency amount, the worker computes it from the open amount and the booked rate: the list's own `RateFC` (option 1), else the `rate` stored for the item from an earlier read in the same currency, which in practice means the incremental sync read must have seen the item at least once. Core `bookedAtRate` does it: rate parsed by core `parseRate` only, exact BigInt arithmetic, the currency scales of both currencies (JPY 0, KWD 3), one rounding half away from zero (ADR 0035), null outside the money range. Examples: USD 1,234.56 at 0.92 `base_per_foreign` = EUR 1,135.80; at 1.0870 `foreign_per_base` = EUR 1,135.75. An item with no rate stays without a booked amount. The result is stored as `computed` and never replaces an amount read from Exact for the same balance. One D1 read per chunk, no Exact calls. Set after checking one invoice both ways (`DEPLOY.md` item 17); a wrong direction would show wrong money, so the setting is admin only, needs a sign-in from the last 15 minutes and is audited (`settings.exact_rate_direction`). **Changing or unsetting the direction clears every `computed` amount in the same batch** as the setting and its audit row (amounts read from Exact stay); the next full sync computes them again with the new direction. A full sync that was already running when the direction changed may still write some amounts with the old direction (it read the setting at the start of its pass); they are `computed` too and the next full pass replaces them (equal rank: the newer value wins).
3. **Dormant until verified.** With nothing switched on and the incremental read off, the booked amount stays empty and the acceptance criterion "a USD invoice shows Booked and the difference the morning after a full sync" is dormant. The first-live checklist (DEPLOY.md step 10, item 17) says how to switch it on.

## What this does not decide
- Whether Exact's `AmountDC` includes earlier revaluations (open decision 3). Option 3 applies the invoice's booked rate to the remainder; if Exact revalues open items, its `AmountDC` differs and the sync read wins whenever present.
- Assumptions to verify live (DEPLOY.md item 17): that the list's `AmountDC`, if it exists, is the OPEN amount in the division currency and not the invoice total; that `RateFC` is the invoice's booked rate and which direction it has; that the sync endpoint's `AmountDC` follows part payments.
- Credit notes: amounts are signed, `bookedAtRate` is odd in the sign, so a negative open amount gives a negative booked amount.
