# 0046 Data quality notifications: e-mail abstraction, instant alerts, daily digest (Phase 8, D8b)

Status: accepted for the code; **the e-mail provider is PROVISIONAL** pending open decision 5 (reminder timing and tone; Exact debtor management or an own e-mail service). Nothing has been sent by this code against a real provider. Code: `packages/core/src/dq/notify.ts` (types, settings, keys, renderers), `apps/worker/src/email/` (sender, log), `apps/worker/src/dq/{alerts,digest,notify-settings}.ts`, routes in `dq/routes.ts`, migration `0027_email_log.sql`. CLAUDE.md 4.6 ("daily digest email, instant alert for critical") is the brief.

## E-mail sending (provisional)

`EmailSender` has two implementations, chosen from a setting:

| Kind | When | Behaviour |
|---|---|---|
| `disabled` | default, and whenever the https sender is incomplete | sends nothing; callers record `skipped_not_configured` |
| `https` | setting `emailProvider = https` with a host and a sender address, and the secret `EMAIL_API_KEY` present | one JSON `POST https://<host>/emails` with `Authorization: Bearer <EMAIL_API_KEY>` and `{from, to[], subject, html, text}`; a 2xx answer may carry `{"id": "..."}` |

**Why this, and not the Cloudflare `send_email` binding.** The binding needs a verified destination or a Cloudflare Email Routing set-up and a code change per environment; an HTTPS call to a configured host needs no binding, works in staging and production with the same code, is trivially mockable (`fetchFn`) and keeps every secret in a Workers secret and every choice in settings. The request shape is that of common transactional APIs (Resend uses exactly this), so a provider is a matter of host, sender and key. **No provider is named in code.** If decision 5 picks Exact's debtor management for reminders, this sender still serves the internal alerts and digest; if it picks a service with another request shape, only `httpsSender` changes. The host is validated as a public DNS name (no IP literal, no port, path or userinfo; the last label must start with a letter, because a URL parser reads `0x7f.0x1` or `017700000001.0` as an IPv4 address; no `localhost`, `.local`, `.internal`, `.arpa`, `.lan`, `.corp`, `.home`, `.test` and similar private zones), https only, re-checked by the sender before every call, and changing it needs an admin with a fresh sign-in (it receives the API key).

**Result classification** is what makes claim-then-send safe:

- 2xx: `sent` (the id is stored when readable, otherwise null). The answer is read through a 16 KiB cap; an id is kept only when it is printable ASCII without spaces, at most 200 characters.
- Before any call the sender refuses (`failed / bad_host` or `bad_message`, nothing sent) a host that is not a public DNS name, a recipient or sender that is not a plain address, more than 100 recipients, or a subject with control or line-separator characters.
- 4xx other than 408 (including 429): `failed`: the provider definitely did not accept it. May be tried again.
- 408, 3xx (redirects are not followed), 5xx, timeout (10 s), network error, a sender that throws: `unknown`: it may have been delivered. **Never sent again by the code.**

## Recipients

Only people in the `users` table: not disabled, not `is_external`, holding role `admin` (mode `admin`) or `admin` or `finance` (mode `admin_finance`, default), **and** whose address is on `ALLOWED_HD` (v1 is domain-only, exact domain, so `x@sub.camelthorncapital.com` and look-alikes are out) and is a plain ASCII mailbox as stored (letters, digits, `+_-` and single inner dots; no display name, list, comment, control or non-ASCII character: lower-casing would turn the Kelvin sign U+212A into "k"). There is no free-text address anywhere: not in a setting, not in a request. The test message goes to the caller only, and only if the caller is such a recipient. Removing a role or disabling a user takes effect at the next send (the list is read per send).

## The e-mail ledger (`email_log`, migration 0027)

The placeholder table of migration 0003 was never written and is replaced. One row per e-mail: unique `idempotency_key`, `kind` (`dq_alert`, `dq_alert_summary`, `dq_digest`, `test`), `template` (`dq.alert.v1`, ...), `recipients_count`, `status`, `attempts` (1 to 3), `dq_issue_id`, `reminder_id` (kept for Phase 10), `provider_message_id`, `error_code`, timestamps. **No address, no subject, no body.** Statuses: `claimed`, `sent`, `delivered`, `bounced`, `failed`, `unknown`, `skipped_not_configured` (`delivered` and `bounced` are for Phase 10's provider callbacks; nothing sets them yet).

Guards (hashes pinned): `email_log_identity` (key, kind, template, recipient count, issue, reminder, created_at never change), `email_log_status_path` (claimed to sent / failed / unknown / skipped; failed to claimed only with attempts + 1; sent to delivered / bounced), `email_log_attempts` (attempts only rise, only with failed to claimed), `email_log_keep_recent` (a row younger than 365 days cannot be deleted).

**Retention.** Rows older than **400 days** are deleted by the alert pass and by the digest job (the delete trigger is the floor at 365 days). The log is small (one row per alert and per recipient and day). Every claim also writes an `email.claimed` audit row (kind, template, recipient count; no address).

## Instant alerts for critical issues

After `dq.checks` has reconciled the issues (`dq/alerts.ts`, called at the end of the run; a failure there never fails the checks, it is counted as `alertsError`):

- **Which issues:** status `open` (never snoozed or resolved), severity `critical`, `notified_at IS NULL` (new, or reopened: the reconcile clears it and raises `reopen_count`), and the last verdict of the rule in `dq_rule_status` is `issues`. A rule that is `not_available`, `not_configured`, `disabled` or `error` vouches for nothing, so its leftover critical issues are not alerted.
- **Claim then send.** One D1 batch (atomic) does three things, each conditional on the same facts: `INSERT email_log` with key `dq-alert:<dq_issues.id>:<reopen_count>` (`ON CONFLICT DO NOTHING`, only while the issue is still open, critical and unnotified), `UPDATE dq_issues SET notified_at` guarded by `changes() = 1`, and the audit row. Only the writer whose insert changed a row calls the sender, so two concurrent runs cannot both send. A reopened issue has a new `reopen_count` and so a new key: it is alerted again, once. **The key uses the issue ROW id, not the fingerprint (review V1 B1):** two administrations can report the same fingerprint, and a row deleted by the 180-day retention can be inserted again while `email_log` keys live 400 days; either would have marked a new critical as notified without sending. Row ids are AUTOINCREMENT and never reused. **Upgrade:** keys written before (`dq-alert:<fingerprint>:<n>`) are still recognised, but only together with the same `dq_issue_id`, so an already alerted open issue keeps its `notified_at` and is not alerted again, while an issue that merely shares a fingerprint is. Nothing is migrated or rewritten.
- **Crash between claim and send.** The row stays `claimed`. A sweep (every alert pass and digest run) turns a claim older than 15 minutes into `unknown / claim_stale`. It is **not sent again**: a duplicate flood is worse than a missing alert, and the gap is visible in the log and in the job summary (`alertsUnknown`). A sender that throws, or a 5xx or timeout, ends the same way.
- **Refusals** (`failed`) are re-claimed (`attempts + 1`) by a later run while the issue is still a pending critical with the same reopen count, at most three attempts in total, and **no sooner than 15 minutes after the last attempt** (V1 S3). A 429 answer (with `Retry-After`, passed on as `retryAfterSeconds` but not stored) is a refusal that also **ends the run's sending**: nothing further is claimed or sent in that run, so the unsent issues stay pending for the next hourly run. The retry query only picks refusals whose issue is still pending in the same life (review D8b), so old refusals of resolved issues cannot hold the 20 retry slots for ever.
- **Once per life, enforced twice.** The end of a snooze keeps `notified_at` (it is not a new life; review D8b changed the D8a reconcile, which cleared it). Before choosing candidates the pass also marks every pending critical whose `dq-alert:<fingerprint>:<reopen_count>` key already exists, without sending: such an issue would otherwise lose its claim every run and keep a single-alert slot for ever, pushing new criticals into summaries.
- **Summaries list what they claimed.** The summary's `UPDATE ... RETURNING id` tells which issues this claim marked; only those are in the message.
- **Cap and fold (V1 S3).** At most `maxAlertsPerRun` (default 10, 1 to 50) mails per run, retries first, then single alerts, oldest first. Everything else that is pending is claimed together and sent as **one summary alert per run** (key `dq-alert-summary:<job run id>:0`), which lists up to ten and states the total. The claim row is written first, then the issues are marked in groups of 80 (D1 allows 100 bound parameters per statement); the message lists only what this claim marked. A summary the provider definitely refuses (`failed`) **gives its issues back** (`notified_at` cleared for exactly the ones it marked), so the next run alerts them again; an `unknown` outcome is never undone. Sends of one run are 300 ms apart (the https sender's `spacingMs`).
- **Cooldown (V1 N2).** A critical whose fingerprint (same administration) was alerted in the last 24 hours (a `claimed`, `sent`, `delivered`, `bounced` or `unknown` row; a refusal does not count) is marked as handled without a mail when it is reopened or re-created; the daily digest still lists it. Only for a rule that was really evaluated, and only when a sender and recipients exist.
- **Counts (V1 N1).** The job result's `alertsSent` is the number of mails the provider accepted; `alertsClaimed` counts claims (singles and retries), `alertsSuppressed` the cooldown skips, `alertsRateLimited` is 1 after a 429.
- **Nothing configured.** With no sender (or no qualifying recipient) nothing is claimed and `notified_at` stays NULL, so enabling the sender later alerts what is still open (subject to the cap). One `skipped_not_configured` row per Amsterdam day (`error_code` `not_configured` or `no_recipients`) shows that alerts were pending.
- **Known limit:** an issue whose alert is `failed` three times or `unknown` has `notified_at` set and is not alerted again until it is resolved and reopens. The log and `alertsFailed`/`alertsUnknown` show it; the daily digest still lists it.

## Daily digest (`dq.digest`)

Job `dq.digest`, daily **08:00 Europe/Amsterdam**, default job row **enabled** (existing rows are never flipped; the seeding inserts the new row on the next start; on an upgraded install this means the digest is on while `dq.checks` may still be off, see below). `DEFAULT_JOBS_VERSION` is now 6: the bump also carries the one-off guard that switches an enabled `exact.bank_balances` row off (audit `job.forced_off`, ADR 0045). It sends **nothing** until the sender is configured: it ends `skipped / email_not_configured` and records one `skipped_not_configured` row for the day. Manual "Run now" needs a fresh sign-in (it sends e-mail).

One e-mail per recipient (key `dq-digest:<Amsterdam date>:<user id>`, claimed before the send). Content: the number first ("6 open data quality issues, 2 critical") **when the checks are alive**, counts by severity and by area (all administrations; issues of rules an admin switched off are not counted, the same rule as `/api/dq/summary`, whose figures are per administration plus the global ones), new since yesterday (first seen in the last 24 hours), snoozed, the oldest open issue, the ten most important open issues (severity, then age) each with a fix link, and **the rules that were not evaluated, with the reason**. Links are `<baseUrl><path>` when a base URL is set, else the relative path. A repeated run finds the claims and sends nothing; a refused recipient is retried alone after ten minutes (job retry, three attempts); an unknown outcome is never retried.

The pure renderer (`renderAlert`, `renderAlertSummary`, `renderDigest` in `packages/core`) HTML-escapes every value that comes from data (issue subjects and messages, rule titles, reasons), puts each on one line capped at 300 characters, builds links only from a base that passes `normalizeBaseUrl` and an app path of the form `/segment/...` (anything else becomes the relative path or `/`), masks IBANs once more (`safeText`, worker side), strips control characters from subjects (no header injection), has a plain-text twin with the same content, no images, no tracking pixels, no external resources. Sentence case, no exclamation marks. Tests assert content, not snapshots.

**State of the checks (V1 S4).** The digest reads the last `dq_runs` row. With no run it leads with "Data quality checks have never run" (subject and first line) and shows no counts; with a last run older than 6 hours it leads with "Data quality checks have not run since <date>" and says the counts are from that run; a last run that was `partial` or `error` adds a line that the counts may be incomplete. A zero is only printed when the checks actually ran. Rules switched off are not in the not-evaluated list. A 429 from the provider ends the digest loop early; the remaining recipients are retried by the job retry. The digest does not make `integrations.job_stale` complain: a run that ends `skipped` with `email_not_configured`, `notifications_disabled` or `no_recipients` is a deliberate skip and is not judged.

**Sender address (V1 N8).** `normalizeFromAddress` is a dot-atom check: no leading, trailing or doubled dot in the local part, domain labels that start and end with a letter or digit, at least two labels, an alphabetic last label of two or more letters.

## Settings API

Setting `dq.notifications` (JSON in `settings`, with a `rev`): `enabled` (master switch, default true), `alertRecipients` (`admin_finance` | `admin`), `baseUrl` (`https://host[:port]` or empty), `maxAlertsPerRun`, and the sender: `emailProvider` (`disabled` | `https`), `emailHost`, `emailFrom`. `GET /api/dq/notifications` (admin) also answers `apiKeyPresent`, `senderActive`, `allowedDomain`, `recipientCount`; **the key's value is never returned**. `PATCH` (admin, step-up, audited `dq.notifications_changed` with before/after, optimistic `rev`, 409 on a stale one, strict validation, a change that changes nothing writes nothing). `POST /api/dq/notifications/test` (admin, step-up) sends one message to the caller, at most one in any 60 seconds (review D8b: the check is inside the claim INSERT, so a clock-minute boundary or concurrent requests cannot get a second one through).

**Deviation from the task text:** there is no `digestHour` setting. The digest hour is the schedule of the `dq.digest` job (Settings, Schedules, admin-editable, validated there); a second copy would only be able to disagree with it.

## Housekeeping (D8a review leftover)

`dq.checks` resolves open and snoozed issues of administrations that are no longer synchronised (`sync_enabled = 0`, connection disabled or gone) with `resolved_by = 'system'`, `resolution_note = 'division_not_synchronised'` and one audit row `dq.unsynced_resolved` (counts only), **after a grace of 7 days** (review D8b). "Disabled" is also what a failed Exact re-authorisation leaves behind (the callback fails closed), and an admin may switch an administration off briefly; resolving at once would drop snoozes and notes and, on return, reopen every issue with a new reopen count, so every critical one would be alerted again. The first check run that sees an administration unsynchronised records the time in setting `dq.unsynced_since` (a map division id to time); an administration that is synchronised again leaves the map, so the grace starts again the next time. Until then only its `dq_rule_status` rows are removed: they vouch for nothing, so no instant alert goes out for that administration (the digest still counts its issues). Global issues (division 0) are untouched. After the grace, if the administration is synchronised again the issue reopens through the normal path.

## Privacy and logging

No log line, error, result summary or audit row contains an address, subject, body, API key or the provider's answer text (a source scan, `dq-notify-scan.test.ts`, checks it). The job summaries hold counts and codes. The `email_log` holds counts and codes. ADR 0045's statement that the data quality code makes no external call stays true for the rules and the check; the alert pass is the one place where `dq.checks` talks to the outside world, through `src/email/sender.ts`, and only to the configured e-mail host.

Screens (done: Data health and Today in D8c, ADR 0047; Settings, Notifications in the Phase 8 review), delivery and bounce callbacks (`delivered`, `bounced`; Phase 10), a Data health path in the web app for summary alerts (done: `DQ_HEALTH_PATH` in core is `/data-health`, the D8c route), notifications to external accountants (v1 is domain-only; open decision 8), per-user opt-out, an alert for a failed or unknown alert, SMS or chat channels.

## Notifications screen and where the data goes (Phase 8 review)

Settings, Notifications (admins only, lazy) edits the sender and alert settings with the `rev` of GET /api/dq/notifications (409 reloads and says so), needs a fresh sign-in like the API, validates with the core normalisers, asks for confirmation when the host changes (the API key will be sent to it) and has a "Send test email to me" button (one per 60 seconds, the refusal and the wait are shown; the server's `retryAfterSeconds` is used when given, at most an hour). The test request has an empty body, so it always uses the saved settings; the button is off while the form has unsaved changes. The host question names the exact `https://<host>`, is asked again if the host changed after it was asked, cannot be answered by Enter from the form (focus moves to the dialog) and warns about punycode (`xn--`) names. A quiet refresh that brings another `rev` while the form has edits shows the same "someone else changed" notice. After a save focus moves to the form heading, after a conflict to the notice. The API key is never shown: only "set" or "not set". The API exposes no `email_log` rows, so the screen shows no delivery history (none was invented).

**Data protection (open decision 5 follow-up).** Alert and digest bodies carry supplier and customer names, invoice numbers and amounts, so they leave the EU storage boundary for the e-mail provider. Before sending is switched on, the provider must process in the EU and a data processing agreement must be signed. The alternative is a minimal body (counts plus a link to Data health). A `bodyMode: full|minimal` setting was not added: the renderers and the worker pass full item data today, so it is more than a trivial core change. It is recorded as a follow-up of open decision 5.
